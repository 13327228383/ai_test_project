## 二、引擎的目标是什么（逐字取自 `AGENTS.md` + 用户 08-28 拍板）

```
总目标：构建一个 通用、智能、媲美高级软件测试工程师 的自动化测试引擎。
```

| 维度 | 定义 | 用户原话锚点 |
|---|---|---|
| **通用** | 跨系统/行业/页面，**键盘鼠标控件的组合**；规则驱动，不依赖特定业务知识。任何修复必须通用，**禁止为特定靶子打补丁** | "通用 = 控件组合，非系统" |
| **智能** | AI 理解需求、自动生成用例、语义验证、自主探索执行——**不是脚本回放**。理解/拆解/生成/控件语义定位/语义验证全程真实 LLM 调用（本地 qwen2.5:7b + 云端强模型双路由）。**AI 调用 = 0 的环节就是智能缺口** | "智能 = AI 判断 + AI 稳定性" |
| **AI 稳定性** | 同输入 → 同输出（已落地 `ai_stability_seed=42` + `temperature=0.0`）；需量化"多次跑结果一致、不抖动" | 尚未系统验证 ← **未做** |
| **易用** | 配置项生效 + 触发/轮询/报告响应可用 + 用户介入成本最低（`is_auto_apply_enabled` 默认 True） | "用户介入越少越好" |
| **工程师水位** | 覆盖正向+异常+边界+安全+性能+可访问性；根因分析；详细 Bug 报告（复现步骤+严重程度）；人机协同审核闸门（Step2/3 后人工审核，Step5 人工补测建议） | 拍板原文 |

**铁律**：理解交给 AI、规则只兜底；禁止表演式/造假式收口；**唯一入口 = 引擎前端模拟真实用户**。

## 六、本轮新发现的两条根因（均已实测证伪到代码行，通用、非靶子补丁）

### 6.1 我的验收脚本自身两次"假完成"（工具层缺陷，已修）

| 版本 | 完成判据 | 结果 | 被什么证伪 |
|---|---|---|---|
| v1 | 行数连续不变 + >60s | t+76s 假完成 | 引擎返回 409「Step 2 正在执行中」 |
| v2 | `POST /api/step/3` 不再 409 | t+25s 假完成 | 引擎日志 11:11:07 仍在 `feature_driven_extract` 本地 LLM 调用（单次 289.9s，timeout=900s） |
| v3 | 目标族新行 / Step2 失败日志 / run_logs 停写 ≥900s | **t+423s 收敛：4/4 点亮** | — （正确判据） |

> 意义：**"看起来安静了"不能作为完成判据**。三种间接信号（行数稳定、步骤探针、`/api/status.running`）本轮全部被实测证伪。验收体系必须把"完成判据"本身列为受验对象。
> v3 最终输出：`coverage 3 / step2_breakdown 9 / step2_confidence 6 / slice_coverage 2`，窗口内无其他族被顺带点亮。

### 6.2 `需求未实现` 假 Bug 群（12 行）—— 两条叠加根因

**现象**：`TC-REQ-008/009/010/011` 的 12 条用例被判 `PRODUCT_BUG`，理由"需求已定义但系统未实现/不可达"。

**根因 A（D22）：nav 清单存在性判据不校验靶子一致性**
- `_agent_executor.py:369` → `_project_has_nav_inventory()`（`_agent_executor.py:23-55`）只做 `SELECT 1 FROM nav_graph_nodes WHERE project=%s LIMIT 1`，**只判存在性**。
- 实测：`modsystem` 的 `nav_graph_nodes` 3 行全部指向 **`http://127.0.0.1:8020/`**、`page_title='SmartShop 商品管理'`、元素是 SmartShop 的（`/products/new`、`+ 新增商品`），**摄入于 2026-09-20 12:17:25**。
- 而 `project_configs.modsystem.TARGET_URL = http://127.0.0.1:8040`（**8020 已无监听**）。
- 即：**一份陈旧且跨系统的残留清单，被当成本系统的菜单清单**，为"需求未实现"提供了伪证据基础 → 走 `_agent_executor.py:391` 的 FAIL 分支。
- 通用性缺陷：任何"靶子端口/域名迁移过"的项目都会中招。

**根因 B（D23）：章节号剥离正则不吃多级编号 → 模块名被破坏**
- `src/pipeline/step3/case_rules/base.py:65`：`re.match(r"^(\d+|[一二三四五六七八九十]+)\s*[\.、．:：]", _m)` — `2.1 商品管理` 匹配 `2.` → 判为"文档章节标题"。
- `base.py:93`：`re.sub(r"^(\d+|[一二三四五六七八九十]+)\s*[\.、．:：]\s*", "", _m)` → 只剥一级，留下 **`1 商品管理`**。
- 引擎日志逐字复现：`module=1 商品管理`（09:22:37）、`module=5 其他零碎的`（多行）——而 DB 里是 `2.1 商品管理` / `2.5 其他零碎的（散落在聊天记录里）`。
- 后果：模块名与侧边栏菜单项失配 → 导航必失败。
- 通用性缺陷：任何**两级编号**的需求文档（`3.2 订单管理` → `2 订单管理`）都会中招。

**叠加效果**：B 破坏模块名 → 导航失败；A 用陈旧清单把"导航失败"升级成"需求未实现" → 假 Bug。

**修复位置（待实施 + 待强模型复核）**：
1. `_project_has_nav_inventory` 增加靶子一致性校验：`page_url` 必须与项目 `TARGET_URL` **同 origin**（或至少同 host:port），否则视为"无清单"。
2. `_is_doc_section_heading` / `_sanitize_doc_heading_module` 的正则改为吃完整多级编号：`^(\d+(?:\.\d+)*|[一二三四五六七八九十]+)\s*[\.、．:：]\s*`。

### 6.3 顺带发现的种子/确定性缺陷
