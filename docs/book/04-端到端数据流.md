# 第 4 章　端到端数据流

## 概述

引擎的五个步骤之间不通过函数调用传递结果，而是通过数据库表传递。这个设计让每一步都可以单独触发、单独重跑、单独查看中间结果，代价是数据流必须写成文档，否则没人能看清一张表是谁写的、谁在读。

本章按步骤列出数据流向。表名全部来自 `src/core/schema.sql` 的真实建表语句，共 **90 张**（该文件内 `CREATE TABLE` 字面出现 94 次，其中 4 次位于注释行，见本章"待核实"）。

## 全局流向

```
                        数据源（文件 / 接口平台 / 设计稿平台）
                                 │
                        ┌────────▼────────┐
              Step1     │  source_documents │  原文与哈希
                        │  source_hashes    │
                        └────────┬────────┘
                                 │
                        ┌────────▼────────┐
              Step2     │  requirements     │  结构化需求条目
                        │  requirement_slices│  切片与覆盖
                        │  clarification_*  │  澄清会话
                        └────────┬────────┘
                                 │
                        ┌────────▼────────┐
              Step3     │  test_cases       │  用例（actions+checks）
                        │  case_meta        │  用例元信息（车道、状态）
                        │  case_requirement_mapping │ 用例↔需求
                        └────────┬────────┘
                                 │
                        ┌────────▼────────┐
              Step4     │  executions       │  执行结论
                        │  run_logs         │  逐步日志
                        │  execution_screenshots / oracle_results │ 证据
                        │  ai_health_metrics │  指标
                        └────────┬────────┘
                                 │
                        ┌────────▼────────┐
              Step5     │  generated_reports│  报告
                        │  coverage_summaries│ 覆盖汇总
                        └─────────────────┘
```

横切表（`nav_graph_nodes`、`rag_chunks`、`capability_cache`、`trace_links` 等）在多个步骤中被读写，不归属单一阶段。

## Step1 · 数据拉取

**入口**：`src/pipeline/step1.py`。**数据源注册**：`src/pipeline/datasource_registry.py`（四个内置源）。

| 表 | 操作 | 内容 |
|:---|:---|:---|
| `source_documents` | 写 | 拉取到的需求原文 |
| `source_hashes` | 写 | 统一哈希表，按 `doc_type` 区分来源，用于增量判断 |
| `source_confluence_hashes` | 写 | Confluence 的逐页哈希 |
| `source_yapi_hashes` | 写 | YApi 的逐接口哈希 |
| `source_breakdown_hashes` | 写 | 拆解阶段的哈希 |
| `document_versions` | 写 | 文档版本记录 |
| `figma_*`（8 张） | 读写 | 设计稿缓存、配额、节点哈希、图片 |
| `pipeline_checkpoints` | 写 | 断点续跑 |

哈希表的作用是增量：内容未变则后续步骤可以跳过。四张哈希表按来源拆开，而不是一张大表加类型列，是为了让不同来源的哈希算法各自演进（逐页 vs 逐接口）。

## Step2 · 需求拆解

**入口**：`src/pipeline/step2.py`。

| 表 | 操作 | 内容 |
|:---|:---|:---|
| `requirements` | 写 | 结构化需求条目（含操作、预期反馈、原文引用、置信度） |
| `requirement_slices` | 写 | 文档切片，用于覆盖度校验 |
| `requirement_slices` / `trace_link_chunks` | 写 | 切片与追溯链接 |
| `clarification_sessions` | 写 | 澄清会话 |
| `clarification_answers` | 写 | 澄清问答 |
| `source_breakdown_hashes` | 写 | 拆解结果哈希 |
| `qa_feedback` | 写 | 质量反馈 |
| `ai_generation_logs` | 写 | AI 生成日志（每次生成尝试一行） |

`requirements` 表是这一阶段的核心产物。它同时记录需求内容与**可追溯信息**（原文引用、置信度），这是防幻觉机制的数据基础（第 28 章）。

## Step3 · 用例建模

**入口**：`src/pipeline/steps/step3/`（生成器）+ `src/pipeline/step3/`（规则体系）。

| 表 | 操作 | 内容 |
|:---|:---|:---|
| `test_cases` | 写 | 用例本体（`actions`、`checks`） |
| `case_meta` | 写 | 用例元信息：类型、复杂度、审核状态、审核车道 |
| `case_requirement_mapping` | 写 | 用例到需求的映射 |
| `review_lane` | 写 | 三车道（green / yellow / red）判定结果 |
| `review_log` | 写 | 审核操作日志 |
| `test_rules` | 读 | 生成用例时参考的规则 |
| `action_categories` / `action_actions` | 读 | 动作库分类与动作定义 |
| `synonym_library` / `project_synonym_overrides` | 读 | 同义词库（定位器解析用） |
| `case_upload_history` | 写 | 外部导入用例的历史 |

`test_cases` 与 `case_meta` 是**一分为二**的：前者存用例内容，后者存元信息与流转状态。分开的原因是审核状态会频繁更新，而用例内容一旦定稿就不该被改动——把高频写与低频写分表，减少行膨胀。

## Step4 · 执行

**入口**：`src/pipeline/step4_executor.py`。

| 表 | 操作 | 内容 |
|:---|:---|:---|
| `executions` | 写 | 每条用例的最终状态与失败原因 |
| `run_logs` | 写 | 执行日志，按 `step_num` 记录步骤序号 |
| `run_summary` | 写 | 一次运行的汇总 |
| `execution_screenshots` | 写 | 执行截图 |
| `oracle_results` | 写 | 视觉预言机的判定结果 |
| `visual_review` / `visual_baselines` | 读写 | 视觉审核结果与基线 |
| `ai_health_metrics` | 写 | 指标（含 `metric_type='token_usage'` 的 token 用量） |
| `coverage_results` | 写 | 单次覆盖结果 |
| `coverage_summaries` | 写 | 覆盖汇总 |
| `step4_op_cache` / `op_cache_v2` | 读写 | 操作缓存 |
| `capability_cache`（3 张） | 读写 | 能力探测缓存 |
| `flaky_guard_history` / `flaky_guard_detected` | 读写 | 不稳定用例识别 |
| `self_heal_patches` / `vision_heal_cache` | 读写 | 自愈补丁与视觉自愈缓存 |
| `action_logs` / `tool_execution_log` | 写 | 动作与工具执行日志 |
| `nav_graph_nodes` / `nav_graph_edges` | 读写 | 导航图 |
| `navigation_match_logs` | 写 | 导航匹配日志 |
| `trace_links` | 写 | 追溯链接 |
| `diff_snapshots` | 写 | 差异快照 |

`executions` 是最关键的一张表。它按 `run_id` 做 UPSERT（同一运行重复执行同一用例是更新而非新增），因此**统计执行进度不能靠数行数**——行数恒定。判定运行是否结束必须另找信号（第 8 章）。

## Step5 · 报告

**入口**：`src/pipeline/steps/step5/report_generator.py`。

| 表 | 操作 | 内容 |
|:---|:---|:---|
| `generated_reports` | 写 | 生成的报告正文与元信息 |
| `coverage_summaries` | 读 | 覆盖汇总 |
| `executions` | 读 | 逐用例结果 |
| `oracle_results` / `visual_review` | 读 | 视觉判定 |
| `ai_health_metrics` | 读 | 指标区块 |

报告以 MySQL 为唯一事实源，读表拼装正文后落回 `generated_reports`。通过率按**用例**粒度计算，`SKIP` 计入分母，`ERROR` 与 `FLAKY` 不计入（第 12 章给出代码位置）。

## 设计取舍

**为什么用表而不是消息队列传递阶段结果。** 全流程落库带来三个直接好处：任一步可单独重跑；中间结果可人工查阅与修改（审核闸门就建立在人工可直接编辑 `case_meta` 的能力上）；出问题时可回溯到具体哪一步写坏了数据。代价是 schema 复杂，90 张表需要维护，且跨表事务较多。

**为什么哈希表按来源拆成四张。** 三个来源（Confluence 逐页、YApi 逐接口、拆解结果）的增量判据不同：页面级哈希与接口级哈希的粒度、算法、失效条件都不一样。合成一张表需要一个类型列加一堆可空字段，反而更乱。

**为什么 `executions` 用 UPSERT 而不是 append。** 重跑同一条用例时，保留历史每次结果会让"当前状态"需要额外聚合才能得出。UPSERT 让表始终表示"最新状态"，查询简单。代价是丢失执行历史——这是刻意的取舍，历史执行记录通过 `run_logs` 保留。
