# 第 31 章　关键设计四 · 语义唯一源

## 概述

一个测试引擎里，同一个语义会被很多地方用到。"这条需求期望的是报错还是成功"——生成用例时要用（决定断言是"检查错误提示"还是"检查成功提示"）、执行时要用（决定表单是否允许自动填充）、校验时要用（决定断言语义是否反转）。如果这三个地方各自写一套判断逻辑，那么当判断标准需要调整时，只要漏改一处，系统内部就出现了两个互相矛盾的"事实"。

这类问题在代码里有个共同特征：**同一个语义被多处各自重新推导，而不是在源头判定一次、下游只读。** 本章讲这套引擎为消除它做了什么，以及还没做完什么。

## 三种失效形态

**形态一：改一处漏一处。** 判断"期望报错"的关键词表在 A 文件里是三组词，在 B 文件里是四组词。改 A 没改 B，于是同一句需求在生成阶段被判为"期望报错"、在校验阶段被判为"期望成功"，断言极性反转。

**形态二：判据分叉。** 同一个常量（例如严重级顺序 `critical > high > medium > low`）在两个模块各写一遍。安全报告按一种排法，可访问性报告按另一种排法，同一份报告里的"严重"含义不一致。

**形态三：注释携带事件叙事。** 某处注释写着"某某日期修复了某某问题"，后来者读到这里会顺着那条已废弃的分支继续加分支，把一次修复变成一道永久的补丁。

## 已收敛的语义

### 期望极性的权威源

判断"这段文本期望的是报错还是成功"，全局只有一处实现：

```
src/pipeline/step3/_rule_extractor_keywords.py:745   expects_error_feedback(*texts) -> bool
src/pipeline/step3/_rule_extractor_keywords.py:734   is_disjunctive_text(text) -> bool
src/pipeline/step3/_rule_extractor_keywords.py:873   _DENY_RE（拒绝语义正则）
```

下游不再各写关键词表，而是调用这个函数。实际调用点例如：

```
src/agent/explorer_mixins/_action.py:1110-1115
    _polarity_texts = [...]
    _allow_autofill = not _expects_error_feedback(*_polarity_texts)
```

执行器判断"这个表单能不能自动填充"，依据是极性函数的返回值——不是自己再扫一遍关键词。

`is_disjunctive_text` 处理的是另一个易错点：需求文本里的"或"（析取）会让单一断言失真（"显示 A 或 B"不能断言必须显示 A）。这个判断同样只有一处实现。

### 执行身份的权威源

"以什么身份执行这条用例"（例如低权用户）的判定，收敛到 `src/pipeline/step3/_identity_assign.py`，其中的未授权态正则 `_UNAUTH_STATE_RE`（`:58`）是全仓唯一实现。此前散落在多处的匿名态、认证态正则被合并为这一条。

### 常量归位

小而关键的常量被提到 `src/core/` 下的单一模块，下游 import 引用：

| 常量 | 位置 | 内容 | 共享方 |
|:---|:---|:---|:---|
| `SEVERITY_ORDER` | `src/core/severity.py:4` | `("critical","high","medium","low")` | 安全报告、可访问性报告 |
| `KNOWN_LOGICAL_TABLES` | `src/core/known_tables.py:4` | 6 张引擎逻辑表名 | 清理模块、权限校验 |
| `BUILTIN_SOURCE_KEYS` | `src/pipeline/datasource_registry.py:21` | `("confluence","figma","yapi","database")` | 数据拉的四个内置源 |

这三个模块的文档串写得很直白，例如 `severity.py` 的第一行是"严重级序唯一事实源 —— security/a11y 报告共用，勿在下游重抄"。把"不要重复"写在文件开头，比写在规范文档里更靠近读者。

## 没收敛的语义

必须说清楚：这套治理**没有全部完成**。

### 极性还没有落成结构化字段

目标状态是：Step2 拆解需求时判定一次极性，写进 `requirements` 表的一个字段，下游直接读字段。实际状态是：`requirements` 表**没有** polarity 列（建表语句 `src/core/schema.sql:754-795`，逐列核对无此字段）。极性仍然靠"文本 + 唯一函数"在调用时推导。

这比"多处各自推导"好得多——判据只有一份。但它比"源头落字段"弱：同一个需求被多次处理时，极性函数会被重复调用，且调用方需要自己准备好文本入参。要从"函数唯一"走到"字段唯一"，需要改表结构并在 Step2 写入，是一次跨层改动。

### 执行身份仍在扫文本

`_identity_assign.py` 虽然把正则收敛到一处，但它仍然是**用正则扫描需求文本来推断执行身份**，而不是读一个结构化的"访问控制"字段。`requirements` 表同样没有对应的访问控制列。这个缺口与上一条同源。

### 检查点类型的注册表与生成侧守卫

检查点类型（`check` 字段的取值）有一张全局注册表，生成侧在发用例前会校验类型是否在执行端注册过。这层校验的存在本身就说明曾经出现过"生成端发射、执行端不认识"的漂移（第 32 章会讲这种漂移如何产生 ERROR）。

## 防线：重复定义门禁

治理不能只靠一次性清理，否则清完会重新长回来。仓库用一道常驻门禁拦截新增：

```
tests/test_core/test_duplicate_definition_gate.py
```

它有两类判据：

| 判据 | 内容 | 测试函数 |
|:---|:---|:---|
| A 类 | 同一文件内同名 `_` 前缀常量（tuple/list/set，≥2 个元素）被定义 ≥2 次 | `test_no_new_duplicate_constant_in_same_file`（`:98`） |
| B 类 | 同一多元素字符串常量（≥3 个元素）出现在 ≥2 个模块 | `test_no_new_duplicate_vocabulary_across_modules`（`:108`） |

B 类允许存量，存量记录在 ratchet 基线里：

```
_BASELINE_A = frozenset()   # :30
_BASELINE_B = frozenset()   # :31
```

**两个基线当前都是空的。** 意味着 A、B 两类判据下现有代码零违规，任何新增重复都会被立即拦下。基线的机制是"只减不增"：清理一处就从基线里去掉一项，永远不能往里加。

## 设计取舍

**为什么用"函数唯一"而不是一步到位"字段唯一"。** 落字段要改表、改写入、改读取，一次动三层；收敛成函数只动一处，且不改变数据结构。先从函数入手是成本更低的第一步，代价是留下了一个未完成的过渡态——这个过渡态必须被写进文档，否则后来者会以为治理已经结束。

**为什么门禁用 ratchet 基线而不是直接清零。** 跨模块的词表统一需要逐个评审（两个模块的"同一词表"可能语义确实不同）。一刀切清零会强迫把语义不同的词表错误合并。基线的做法是：存量放行、新增禁止，清理按自己的节奏推进。当前基线已空，说明这个节奏走到了终点。

**为什么把"勿在下游重抄"写进模块文档串。** 规范文档（`AGENTS.md`）离代码远，改代码的人不一定读。把一句话写在 `severity.py` 的第一行，读者在 import 它的时候就会看到。这是"把约束放在最靠近决策点的地方"的做法。
