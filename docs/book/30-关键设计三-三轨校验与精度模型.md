# 第 30 章　关键设计三 · 三轨校验与精度模型

## 概述

Step4 的断言 `check` 形如 `{track, precision, check, expect}`，`track∈{ui,api,db}`，`precision∈{exact,fuzzy}`。本章回答为什么断言要分三轨而不是只看界面，为什么 `precision` 是唯一的"分支开关"而非按 `track` 分叉，以及 `decide_verdict` 如何把多轨多 check 聚合成一个用例结论。

## 问题：为什么断言要分三轨

只看界面会漏掉接口与数据层的真实失败。历史实现三轨恒为布尔且无 `UNKNOWN`——Agent 路径未发起 API 调用也被硬赋 `True`，造成"未验证=通过"的假 PASS（`tracks.py:9`–`:12` 的设计动机）。引入 `TrackStatus` 枚举（`tracks.py:26`）：`PASS`/`FAIL`/`UNKNOWN`，并规定非 `UNKNOWN` 状态必须带非空 `evidence_ref`，否则构造期抛错 fail-fast（`tracks.py:54`–`:70`）。`UNKNOWN` 显式表达"未执行"，使门禁与报告能正确区分"通过"与"没验证"。

轨道由 `infer_required_tracks`（`src/pipeline/steps/step4/verification/_tracks.py:58`）推断：优先消费 `verification_plan.required_tracks`，兜底按各轨 `assertion` 非空性推断，`ui` 恒在（`:79`、`:91`）。

## 机制一：precision 是唯一分支开关

断言的分支不按 `track` 分叉，而是按 `precision` 在每个 handler 内部分支。`normalize_check` 将缺省 `precision` 置为 `fuzzy`（`_track_protocol.py:184`）。同一个 `text_contains` handler 内：`precision=="exact"` 只做逗号拆分、不做 2 字子词扩展，逐元素精确匹配（`:270`）；`precision=="fuzzy"` 先做 2 字子词扩展再匹配 `body.innerText`（`:372`）。

这一设计的动机是修复假 PASS：2 字子词扩展曾同时作用于 exact 与 fuzzy，导致 exact 下"科目名称"匹配到仅含"科目"的元素（假 PASS），故 exact 模式剥离扩展（`_db_ui.py:265`–`:268`）。

## 机制二：exact 规则判定与 fuzzy 判定的分工

- **exact**：严格规则判定。子串/等值精确匹配，无歧义时不调用 AI，结果确定、可复现。失败模式是被过度扩展污染（已修复）或断言措辞与界面字面不一致导致误 FAIL。
- **fuzzy**：放宽规则（2-gram 子词扩展）后匹配；对仍存语义歧义的断言，由 `semantic_check` 走"机械优先、AI 兜底"路径——先机械命中并做判别力守卫（`:2196`），判别力不足再升级分页或 AI 判定（`_db_ui.py:2328` `semantic_source="ai"`）。失败模式是扩展过宽造成假 PASS，或 AI 判定误判造成假 FAIL/假 PASS。

## 机制三：断言注册表 _UI_CHECK_DISPATCH

UI 轨 handler 通过 `_UI_CHECK_DISPATCH` 字典分发（`_db_ui.py:2870`）。历史上未注册或命名错位的 check 类型会落入 `else` 分支返回 `passed=True` 或 `UNSUPPORTED_CHECK`，造成假 PASS/假 FAIL（`:894`–`:896`）。注册表持续补齐裸名别名（如 `style`→`_handle_style_check`、`:2908`）与孤儿验证器（`:2919`–`:2945`），把"生成端发了、执行端不认"的缺口堵上。

## 机制四：终判 decide_verdict 聚合多轨

`decide_verdict`（`src/pipeline/steps/step4/verification/verdict.py:36`）是全仓唯一决定用例最终结论的纯函数，置信度阈值 `CONFIDENCE_THRESHOLD=0.70`（`verdict.py:28`）。真值表：

1. `status != PASS` → 维持原状态（FAIL/MANUAL_REVIEW/UNKNOWN 不二次改判，`:62`）；
2. `status==PASS` 但任一轨 `UNKNOWN` → 降级 `UNKNOWN`（未验证不得通过，`:72`）；
3. `status==PASS` 但 `confidence` 缺失（None）→ `UNKNOWN`（`:84`）；
4. `status==PASS` 但 `confidence < 0.70` → `FAIL`（假 PASS 拦截，`:91`）；
5. 全轨非 UNKNOWN 且 `confidence ≥ 0.70` → `PASS`（`:100`）。

阈值防御性只允许上调不可下调（`:54`–`:59`）。0.70 的作用是拦截低置信度的假 PASS：当断言实质未证伪却标记通过时，置信度不足即判 FAIL 而非放行。

## 机制五：四种状态的判定条件

三轨层状态为 `PASS`/`FAIL`/`UNKNOWN`（`tracks.py:26`）。用例层状态在此基础上扩展：

- **PASS**：经 `decide_verdict` 规则 5 聚合通过。
- **FAIL**：执行确实失败，或 `decide_verdict` 规则 4 因低置信度拦截产生。
- **SKIP**：策略 0（actions 与 checks 皆空，`strategy_router.py:134`）或数据不足/阻断门禁导致不执行。
- **ERROR**：setup 或编排异常（如 `step4_executor.py` 的 TDL fail-closed 编排失败，`:813`），与产品缺陷 FAIL 区分。

设计意图：SKIP/ERROR 必须显式可见，不得被静默丢弃或误算为 PASS，否则会掩盖"未测"与"环境故障"。

## 设计取舍

- 三轨 + UNKNOWN 用状态显式性换掉了旧版"布尔硬赋"的便利，代价是每个非 UNKNOWN 结果必须携带证据引用。
- `precision` 作为唯一分支开关统一了三轨的判定逻辑，避免了"按 track 各写一套 exact/fuzzy"的爆炸组合；代价是 exact 措辞敏感，需在生成端保证字面一致。
- 0.70 只上调不可下调，优先保证拦截假 PASS，代价是可能把边界用例判 FAIL，需人工复核。
