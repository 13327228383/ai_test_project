# 第 14 章　横切质量门禁

## 概述

横切质量门禁在任意执行后端上以同一 helper 挂载，覆盖可访问性、安全、性能、视觉四个运行时维度，并叠加 `quality/` 下的用例级三轨校验（rule_check / cross_check / deep_check）。门禁编排收敛在 `src/pipeline/steps/step4/empirical/cross_cut_gates.py`，各维度独立 fail-safe：异常只记录、不阻断用例 PASS/FAIL、不伪造 PASS。本章逐维度说明采集与判定，以及性能基线的校准与回写策略。

## 门禁编排入口与 fail-closed 语义

同步入口 `run_cross_cut_gates`（`cross_cut_gates.py:213`），异步入口 `run_cross_cut_gates_async`（`cross_cut_gates.py:423`）。两者返回同构字典：

```python
{"a11y": {...}, "perf": {...}, "visual": {...}, "security": {...}, "usability": {...}}
```

`cross_cut_gates.py:231-237`，异步版在 `:439-448`。security 经 `_run_security_bundle`（`cross_cut_gates.py:451`）聚合 OWASP DOM 扫描与 RBAC 越权探针。`summarize_cross_cut`（`cross_cut_gates.py:470`）仅产出诊断日志，不改判定。

fail-closed 体现有三处：每个门禁异常时返回 `NO_DATA`/`error` 而非 `passed=True`（如 `run_a11y_check` `cross_cut_gates.py:31-34`、`run_visual_gate` `:82-85`）；`run_security_gate` 异常返回 `total=0` 不伪报（`:99-103`）；`run_authz_gate` 无 `authz` 配置时 `enabled=True, total=0` 诚实跳过（`:127-130`）。门禁结果不进入用例 PASS/FAIL 决策链，仅作为旁路证据。

注：编排结果实际返回 5 个键（a11y/perf/visual/security/usability），而"5D"在任务书中表述为"a11y、security、perf、visual + 原有三个校验维度"，两者计数口径不一致，映射关系见待核实。

## a11y 可访问性门禁

规则集定义在 `src/extensions/a11y/checker.py`，纯 `html.parser` 收集 + 后处理判定，无第三方依赖（`checker.py:1-34`）。共 22 条规则 R1–R22（`checker.py:5-26`），severity 分级 `critical/high/medium/low`（`SEVERITY_ORDER`，`checker.py:43`）。代表性规则：`img-alt-missing`(high)、`input-no-label`(high)、`aria-hidden-focusable`(high)、`media-no-caption`(high)、`nested-interactive`(medium)、`html-lang-missing`(medium)、`tabindex-positive`(low) 等。

采集与判定：`run_a11y_check`（`cross_cut_gates.py:24`）包装 `a11y_checker.run_a11y_check`，返回 `{enabled, findings, total, by_severity}`。异步栈经 `run_a11y_check_async`（`cross_cut_gates.py:37`）走静态快照（`_StaticPage`，`cross_cut_gates.py:240-266`）以复用同步判定。

口径差异：`cross_cut_gates.py:25` 的 docstring 称"8 条可解释规则"，而 `checker.py` 实际定义 22 条（R1–R22）。实际生效以 `checker.py` 为准，docstring 待修正。

|:---|:---|:---|
| SQL 注入 | `SQL_PATTERNS`（含 SQLite 错误泄露 critical） | `__init__.py:50` |
| XSS（反射/DOM/伪协议） | `XSS_PATTERNS`，`rule_id="XSS-001"` | `__init__.py:66,294` |

| IDOR | `rule_id="IDOR-001"`，跨身份同路径数据对比 | `__init__.py:220-587` |

门禁入口 `run_security_gate`（`cross_cut_gates.py:88`）→ `security_checker.run_security_check`。HEAD-001 判真前会探测页面顶层文档响应头并注入 `security.headers`（`:229-230`，`_normalize_headers` `:169-178` 解决 HTTP 头大小写）。越权子维度 `run_authz_gate`（`cross_cut_gates.py:106`）复用 `AuthzMatrixVerifier`，覆盖 allow/deny/allow_self_only/deny_but_suspect 与水平/垂直越权，无配置诚实跳过。

任务书与 `cross_cut_gates.py:89` 注释还列"敏感信息泄露"与"路径遍历"，但 `security_scanner/__init__.py` 中未发现对应独立 `rule_id`，归并判定需核实。

## perf 性能门禁（采集→门禁→相对基线回归三层）

性能体系构建在 `src/extensions/perf_baseline/`，分三层，与 `cross_cut_gates` 解耦：

1. 采集层 `collector.py`：`collect_web`（`collector.py:228`）、`collect_api`（`collector.py:295`）抓 Web 导航计时与 API 耗时/状态码/响应体。`run_perf_check`（`cross_cut_gates.py:58`）→ `perf_checker.run_full_perf_check`。
2. 门禁层 `gate.py`：`evaluate_gate`（`gate.py:136`）为**唯一判定入口**，纯函数、不 IO、永不抛异常。短路优先级（`gate.py:6-13,163-251`）：采集失败/无指标→`NO_DATA`；任一超绝对阈值→`FAIL`；无基线→`BASELINE_ESTABLISHED`；相对基线上浮 ≥ `fail_pct`→`FAIL`，∈`[pre_gate_pct, fail_pct)`→`PRE_GATE`；其余→`PASS`。`status_code`/`resource_count` 仅做绝对校验（`NON_RELATIVE_METRICS`，`gate.py:55`）。`blocking` 仅由 FAIL 数决定（`gate.py:286`）。
3. 相对基线回归层 `regression.py` + `baseline.py`：`regression.py` 跨轮对比当前与前一轮门禁状态，检测 `new_fail`/`new_pre_gate`/`degraded`/`improved` 等漂移（`regression.py:58-65`），与 `gate.py` 的单轮判定互补。

规则配置唯一源 `perf_rules.yaml`：`defaults` 与 `targets.<name>` 递归深合并（`perf_rules.yaml:5`）；绝对阈值原则为"实测 p95 × 1.5"以避免开箱即红（`perf_rules.yaml:11`）。Web 组 7 指标（ttfb/dcl/load/resource_count/resource_bytes/longtask/cls）与 API 组 3 指标（elapsed/status_code/payload）含缺省阈值（`perf_rules.yaml:30-59`）；`smartshop`/`projecthub`/`api_demo`/`spa_demo` 有靶子专属覆盖（`perf_rules.yaml:68-119`）。相对阈值 `pre_gate_pct=80`、`fail_pct=100`（`perf_rules.yaml:61-63`）。

## 性能基线校准与回写策略

基线按靶子分文件存 `baselines/<target>.json`，由 `BaselineManager`（`baseline.py:57`）读写。聚合回写：`BaselineManager.update`（`baseline.py:191`）用本轮样本聚合各指标 `mean`，`baseline_version + 1` 后原子落盘（tmp + `os.replace`，`baseline.py:159`）。`reset`（`baseline.py:258`）清空 entries 保留 target。`get_entry`（`baseline.py:176`）返回 `None` 表示首次见到该 key，对应门禁判 `BASELINE_ESTABLISHED`（首轮不相对判定）。

校准原则（代码层面）有两处：绝对阈值由 `perf_rules.yaml` 手工按 p95×1.5 给定（`perf_rules.yaml:11`）；基线 `mean` 由历史样本滚动聚合自动回写（`baseline.py:191-253`），无独立"自动重新校准阈值"函数，阈值仍靠人工维护。

## 视觉审核门禁（VLM 调用）

`run_visual_gate`（`cross_cut_gates.py:74`）→ `step4/empirical/visual_checker.py:60`。VLM 判定经 `_run_vlm_off_loop`（`visual_checker.py:29`）复用 `_verify_visual._try_vlm_fallback`，链路为云端 → `VLMOracle` → Local 本地降级（`visual_checker.py:11`）。同步执行器用 `asyncio.run` 包装异步 VLM 判定（`visual_checker.py:13-14,146`）。VLM 不可用一律返回 `NO_DATA`（`passed=None`，绝不伪造 PASS，`visual_checker.py:10,148`）。

## quality 用例级校验与部署预览

`quality/baseline_health.py` 的 `BaselineHealthChecker`（`baseline_health.py:47`）检查 5 类基准（YApi API 路径 / Figma UI 元素 / DB 枚举值 / 追溯链路 / DB Schema），整体状态 `healthy/degraded/critical`（`baseline_health.py:89-97`），`can_run_cross_check = yapi或figma或enum存在`（`baseline_health.py:101-103`）。`quality/risk_analyzer.py` 的 `assess_requirement_risk`（`risk_analyzer.py:550`）经 KNN / 语义 / 关键词 / LLM 回退四级评估需求风险。

`quality/case_validator/` 提供三轨用例校验：`quick_rule_check`（纯代码）、`ai_deep_check`（Flash 逻辑矛盾）、`run_cross_checks`（API/UI/枚举/DB 追溯，零 AI，error 级阻断）（`case_validator/main.py:50-54`）。这是任务书所述"原有三个校验维度"的落点。

`deployment/` 为部署文档预览与匹配：`preview.py:preview_versions`（`preview.py:18`）解析转测范围表格供前端版本下拉；`parser/` 提供 `parse_markdown_sections`/`detect_transfer_scope_section`/`parse_table`/`filter_by_version`（`deployment/parser/` 各文件）；`matcher/` 做语义匹配。该模块属文档侧横切能力，不直接参与运行时门禁判定。

## 设计取舍

- 门禁旁路化（fail-safe 不阻断 PASS/FAIL）：保证横切维度缺失/异常不污染主判定，但门禁结论需另一条证据链消费，否则易"亮了没人看"。
- 性能判定纯函数化（`evaluate_gate` 无 IO）：可单测全覆盖，但绝对阈值靠 YAML 手工维护，自动化程度止于基线 `mean` 回写。
- a11y 纯标准库 `html.parser`：零依赖、确定性强，但无法覆盖运行时布局类问题（如点击目标尺寸），后者由 usability 门禁补位。
- security 把 OWASP DOM 扫描与 RBAC 越权合入同一 `security` 键：维度内聚，但 `authz` 纯 API、不依赖 page，调用约定与其他子维度不同。
