# 第 29 章　关键设计二 · 单管道三策略

## 概述

Step4 执行阶段面对的用例数据完整度参差不齐：有的 `actions` 和 `checks` 俱全，有的只有成功标准没有操作路径，有的只有操作没有断言。本章回答为什么不为"确定性执行"和"AI 执行"各建一条独立路径，以及 `_select_strategy` 如何按数据完整度把三种策略汇入同一条验证管道（`steps_from_case` 入口）。

## 问题：为什么不做两条独立执行器

若维护"确定性执行器"与"AI 执行器"两条独立代码路径，会出现两类问题：其一，同一断言在两条路径中各有一套实现，行为口径不一致，同一用例可能得出不同结论；其二，两套路径各自维护动作执行、证据采集、三轨验证，重复成本高且易漂移。引擎选择"单管道 + 策略分支"：执行与验证的实现只写一份，策略只决定"动作从哪来、断言如何达成"。

## 机制一：按数据完整度选策略（四象限）

`_select_strategy`（`src/pipeline/steps/step4/strategy_router.py:30`）是纯函数，依据 `actions`/`checks` 是否非空返回四类结果，常量定义在 `:22`–`:25`：

| actions | checks | 策略 | 常量 |
|:---:|:---:|:---|:---|
| 有 | 有 | 1 确定性执行 | `STRATEGY_DETERMINISTIC=1` |
| 无 | 有 | 2 AI 自主探索 | `STRATEGY_AI_EXPLORATION=2` |
| 有 | 无 | 3 纯动作执行 | `STRATEGY_PURE_ACTION=3` |
| 无 | 无 | 0 跳过 | `STRATEGY_SKIP=0` |

判定只看列表长度是否大于 0（`:50`–`:51`）。人工超驰 `forced_strategy` 在 `:54` 进入，并对前提做校验：策略 1/3 要求 `actions` 非空，策略 2 要求 `checks` 非空，违规则落入 `STRATEGY_SKIP` 并返回 `error` 码（`:66`–`:90`）。

## 机制二：入口统一分发

`steps_from_case`（`src/pipeline/steps/step4/browser_intent_parser/_steps.py:383`）是执行步骤构造的统一入口。它先调用 `_select_strategy` 得到策略（`_steps.py:405`），再按策略号分派：策略 0 直接返回空列表（`_steps.py:408`）；策略 1/2/3 各自构造步骤后汇入验证阶段。入口的单一性保证了"选策略"与"写步骤"不分散在多处。

## 机制三：三策略共用同一条验证管道

三条策略的差异只在"动作从哪来"，验证环节复用同一套构建函数：

- 策略 1 调用 `_build_verify_step`（`_steps.py:311`）构建 `verify_step`，并把 `api_checks`/`db_checks`/`ui_checks`/`required_tracks` 挂回 `step_entry`，使后续三轨验证可执行（`:423`–`:449`）。
- 策略 2 同样调用 `_build_verify_step`（`:480`），与策略 1 共用，仅在前置多一个 `exploration_step`（AI 探索）步骤（`:483`）。
- 策略 3 无 `checks`，用 `_build_basic_verify_step`（`_steps.py:365`）产出与策略 1/2 同形状的验证步骤（仅含一条 fuzzy UI 基础验证），保证三策略汇入同一条验证管道。

`_build_verify_step` 从 `checks` 结构化出三轨列表（`:328`），`checks` 非空却结构化全空的非法用例被强制标记 `required_tracks=["ui"]` 并注入一条 `expect="FAIL"` 的哨兵断言（`:346`–`:359`），避免"格式不合法却被放行"。

## 机制四：策略 2 输入是结构化 checks 而非自由文本

策略 2 的 AI 探索以结构化 `checks` 为输入，而非自由文本目标。`_build_check_list`（`_steps.py:91`）把 `checks` 渲染为"成功标准"清单，注入 AI 的约束 prompt（`:469`–`:475`）。结构化 `checks` 携带 `track`/`precision`/`expect`，AI 据此规划操作，验证阶段仍由 `_build_verify_step` 的三轨管道客观判定，避免 AI 既定目标又自判通过造成的口径失真。

防空转：生成端只产 `test_steps` 而未产 `actions` 的用例，纯靠 `checks` 让 AI 自由探索会在分页/表单页反复空转约 3 轮后触发早停并假 ERROR（`_steps.py:464`）。引擎把已知操作路径 `test_steps` 作为"参考指引"（非强制）注入 prompt（`:476`–`:479`，截断 1500 字），使探索有路径但不被钉死。

## 边界与代价

- 数据不全时策略 2 必然产生 AI 调用成本，且探索路径不可复现；`known_steps` 注入缓解了空转，但探索本身仍非确定性。
- 策略 1 超驰（人工指定但 `checks` 为空）走 `skip_verification` 分支，只执行动作不做三轨验证（`_steps.py:435`），这是为容忍用例矛盾而放开验证，代价是该类用例无法获得断言证据。
- `browser_core/serial.py` 与 `parallel.py` 是实际动作执行后端，三策略构造的步骤最终由二者调度；策略与串行/并行的具体映射关系未在本章精读，见待核实。

## 设计取舍

- 单管道牺牲了"为 AI 路径定制优化"的灵活性，换来了断言口径统一与维护单一性，对防假 PASS/假 FAIL 收益大于代价。
- 结构化 `checks` 约束 AI 而非放任自由文本，把"探索不确定性"关在动作规划层，验证层仍由规则/三轨客观判定。
