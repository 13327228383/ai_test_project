# 第 16 章　检索与知识资产

## 概述

本章覆盖检索与知识资产相关的横切子系统：`src/extensions/rag_engine/`（RAG 引擎）、`src/extensions/semantic_index/`（语义嵌入工具）、`src/extensions/change_impact_kb/`（变更影响知识库）、`src/extensions/system_data_resolver/`（被测系统数据解析器）、`src/extensions/traceability/`（可追溯性），以及独立包 `src/rag/`（多模态块存储与检索）。

这些系统的共同职责是：把需求、API 契约、数据库 schema、DOM 快照、设计稿等异构数据源，结构化并存为可被检索的"知识资产"，供 Step2/Step3/Step4/Step5 复用，并把"需求—用例—执行结果"串成可查询的链路。

## RAG 引擎（`rag_engine`）

`RagEngine`（`src/extensions/rag_engine/engine_core.py:34`）是检索核心，继承自四个 mixin：`ChunkingMixin`、`EmbeddingMixin`、`SearchMixin`、`PersistenceMixin`。

### 向量库与文本存储

代码注释明确声明向量与文本一律走 MySQL `rag_chunks` 表，不再使用 ChromaDB 文件存储（`engine_core.py:71`）。`build_index` 把分块结果批量写入 MySQL（`engine_core.py:317`），`retrieve` 从内存 chunks 做向量/关键词比较（`engine_core.py:339`）。因此本引擎的"向量库"是 MySQL 关系表 + 进程内 Python 计算的余弦/点积，并非独立的向量数据库。

### 嵌入模型

嵌入由 `EmbeddingMixin`（`src/extensions/rag_engine/embedding_mixin.py`）按 `embed_provider` 路由：

- `disk`：本地 `sentence_transformers.SentenceTransformer`，模型名读 `config.disk_embed_model`，缓存目录固定为 `models/sentence-transformers/`，`local_files_only=True` 不联网（`embedding_mixin.py:163`）。
- `ollama`：本地 Ollama `/api/embed`（`embedding_mixin.py:236`）。
- `cloud`：走 `ai_brain._call_api(task_type="embedding")`（`embedding_mixin.py:279`）。
- 全部失败则 `_fallback_embed` 退化为基于字符 n-gram 的 128 维哈希向量（`embedding_mixin.py:303`）。

`RagEngine._EMBED_DIM` 取自 `pipeline_config.rag_embed_dim`，默认 128（`pipeline_config.py:771`，环境变量 `RAG_EMBED_DIM`）。`engine_core.py:58` 定义的 `_EMBED_MODEL_CANDIDATES` 元组在全仓未被引用，属遗留常量（**已核实 2026-10-15**：全仓检索仅 1 处命中，即定义处本身，确认零引用）。

### 切片与召回策略

`build_index` 用线程池并行构建多类分块（`engine_core.py:214`），分块函数定义在 `src/extensions/rag_engine/_index_builders.py`：`_build_dom_chunks`、`_build_api_chunks`、`_build_db_chunks`、`_build_feature_chunks`、`_build_prototype_chunks`。v5 版本起 RAG 只保留 API/DB/DOM/Figma/Feature/Uploads 分块，需求原文改为直接查 `requirement_slices` 表，不再生成 requirement chunk（`engine_core.py:139`）。

召回走 `SearchMixin`（`src/extensions/rag_engine/search_mixin.py:20`），实际实现拆到 `search_mixin_mixins/`：向量检索 `_vector.py`、混合检索 `_hybrid.py`、BM25 `_bm25.py`、rerank `_rerank.py`、入口 `_search.py`。rerank 默认关闭（`pipeline_config.py:512` `RAG_ENABLE_RERANK=False`），开启时检索取 `top_k*3` 候选再重排（`engine_core.py:416`）。`rag_filter.filter_rag_chunks`（`src/pipeline/steps/step4/verification_plan_builder.py:563`）在构建 API/DB 校验计划时过滤 chunks；`rag_usage_logger` 记录每次检索。

## 语义索引（`semantic_index`）

`src/extensions/semantic_index/` 是更低一层的嵌入工具，对外只暴露 `embed()`、`cosine()`、`similarity()`、`get_model_status()`（`_index.py`）。

`embed()`（`_index.py:16`）同样按 `embed_provider` 路由：disk 模式加载 `sentence_transformers` 模型（384 维原生，归一化），ollama 模式截断/补零到 384 维，cloud 模式委托 `RagEngine._embed_text`，未配置则退化为 n-gram（`_ngram.py`）。`get_model_status` 在 disk 模型加载成功时 `dim` 报 384（`_index.py:136`）。

与 RAG 的关系：`semantic_index` 是共享的向量工具层，被置信度计算器用于计算 `semantic_align`（`_calculate.py:302` 引用 `from src.extensions.semantic_index import similarity`）。`RagEngine` 自身在 `embedding_mixin.py` 内有一套平行且近似重复的 disk/ollama 嵌入逻辑，二者共用同一套 `embed_provider` 配置，但代码不共享实现。

## 变更影响知识库（`change_impact_kb`）

`ChangeImpactKB`（`src/extensions/change_impact_kb/kb.py:57`）解决的问题：需求或代码变更后，如何定位需要回归的用例，避免全量重跑。

构建阶段 `build_from_engine` 读取 `executions` 表（最近 5000 条，取 case_id/status/confidence/expected/actual/details）与 `project_configs` 的功能域（`kb.py:103`），构成 `cases` 与 `areas`。`recommend`（`kb.py:179`）有两种模式：

- `impact_driven`：给定变更信号（如改了某页面/接口），先做已知功能域直接匹配，再对每条用例做 Jaccard 词重叠（`_overlap_score`，`kb.py:35`），乘以风险权重 `_RISK_WEIGHT`（`FAIL/ERROR=3.0`、`PARTIAL=2.0`、`SKIP=0.3`、`BLOCKED=1.2`、`PASS=1.0`，`kb.py:19`）与低置信加分，输出受影响用例清单。
- `risk_priority`：无变更信号时，按历史风险全局排回归优先级。

可调参数 `min_similarity`（默认 0.3）、`top_k`（默认 20）由调用方通过 `cfg` 注入（`kb.py:180`）。无 DB 时知识库退化为空，不阻断报告生成。

## 被测系统数据解析器（`system_data_resolver`）

`SystemDataResolver` 解析被测系统的数据源与表结构。

`ResolverConstants`（`src/extensions/system_data_resolver/constants.py:5`）定义列名匹配模式与排除规则：`USER_NAME_PATS`/`USER_PWD_PATS` 用于识别用户表，`ROLE_*` 识别角色表，`EXCLUDE_TABLE_KW`（log_/_audit/history 等，`constants.py:45`）与 `SYS_TABLE_PREFIXES`（sys_/pg_ 等，`constants.py:69`）排除非业务表。

`DbAccessMixin`（`src/extensions/system_data_resolver/db_access.py:11`）按 `db_type` 分支查询：mysql 走 `information_schema.TABLES`/`COLUMNS`（`db_access.py:57`），yasdb/oracle 走 `USER_TABLES`/`USER_TAB_COLUMNS`，postgresql 走 `information_schema`，sqlite 走 `sqlite_master`；列元数据、索引查询均用参数化 SQL（`db_access.py:115`）。`_safe_name` 净化表名/列名防注入（`db_access.py:72`）。

`HeuristicMixin._classify_tables`（`src/extensions/system_data_resolver/heuristic.py:15`）依据列名命中模式，给每张表算出 user/role/entity 分类，并通过外键约束 `_discover_fk_from_constraints`（`heuristic.py:130`）反查 user→role 关联。解析结果写入 `system_data_catalog.json` 缓存，默认 90 天有效（`constants.py:8`）。

## 可追溯性（`traceability`）

`TraceabilityEngine`（`src/extensions/traceability/engine.py:39`）构建"需求↔资源↔用例↔执行结果"的链路。

主事实源是 MySQL `trace_links` 表（`engine.py:102`）。`build_trace_links` 优先从 MySQL 加载缓存，命中阈值 `traceability_cache_hit_threshold` 默认 0.9（`engine.py:47`）；缺失时由 `DataSourceExtractor` 取 API 列表、DB 表、页面，经 `AIBuilder` 构建，AI 不可用则 `HeuristicBuilder` 回退（`engine.py:160`）。`TraceLink`（`src/extensions/traceability/models.py:11`）持有 `api_endpoints`/`db_tables`/`figma_pages`/`chunk_links`/`related_reqs`/`feature_id`。

链路查询集中在 `TraceabilityQueries`（`src/extensions/traceability/queries.py:12`）：`get_apis_for_req`/`get_tables_for_req`/`get_pages_for_req` 正向查询，`find_reqs_by_api`/`find_reqs_by_table`/`find_reqs_by_feature` 反向查询。覆盖率由 `TraceabilityCoverage` 计算 API/DB/页面覆盖(`engine.py:187`)。执行结果侧，用例经 `executions` 表落库，`change_impact_kb` 与报告均从同一张 `executions` 读取，形成"需求→用例→执行结果"的闭环查询。

## 设计取舍

- **MySQL 单一事实源**：RAG 分块、trace_links、diff_snapshots 全部落 MySQL，放弃 ChromaDB 文件存储与 `trace_links.json` 运行时兜底，换取跨进程一致性与可迁移。代价是向量相似度在 Python 进程内计算，大规模 chunks 有内存与算力成本。
- **provider 路由而非硬编码模型**：embedding 完全由 `embed_provider` + 配置驱动，disk/ollama/cloud 各自独立失败、不互相兜底，避免"误降级到错误模型"引发的静默质量下降。
- **启发式 + AI 双轨**：traceability 与 system_data_resolver 都先尝试 AI/external 数据源，失败退化为列名模式启发式，保证无网络/无 LLM 时仍能产出可用链路。
