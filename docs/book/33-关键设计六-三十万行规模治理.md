# 第 33 章　关键设计六 · 三十万行规模治理

## 概述

这套引擎的 `src/` 有 1,163 个 Python 文件、约 29.2 万行。作为参照：它封装的 Playwright 本体约 20 万行，pytest 约 3 万行。一个包着 Playwright 的编排层写到与基础设施同一量级，这件事本身需要解释。

仓库里有一份专门回答这个问题的测量报告：`audits/规模根因诊断_2026-10-04.md`。它用 AST 级全量测量定位膨胀机制，并给出量化收敛路径。本章以这份报告为起点，说明规模是怎么来的、已经收敛到什么程度、以及用什么机制防止回退。

## 膨胀的机制

那份报告的结论是：**不是写多了，是从未收拢过。** 它先排除了三个常见嫌疑：

| 嫌疑 | 测量结果（2026-10-04） |
|:---|:---|
| 复制粘贴堆出来的 | 语义同构克隆家族 ≈ 0（仅 1 个 45 行的小家族） |
| 死代码残留 | 已清零 |
| 注释泛滥 | 注释与文档串仅占 18% |

真正的原因是**防御样板在巨型函数内逐层累积**：

| 指标 | 数值（2026-10-04） | 含义 |
|:---|---:|:---|
| 净代码行（去注释与空行） | 237,914 | 函数 6,025 个、类 550 个 |
| ≥100 行的巨型函数 | 521 个 = 103,850 行 = 净代码 44% | 最大单函数 1,466 行 |
| try/except 机器内的代码 | ≈ 108,500 行 ≈ 净代码 46% | 5,200 个 try 块，try 密度 0.86 / 函数 |

最大那个函数的解剖很能说明问题：1,466 行 = 37 个 try + 36 个处理器 + 89 个 if + 73 次日志 + **0 个内嵌函数**。平均每 40 行就裹一层防御。

成因链是：每个缺陷都在"症状出现的那一层"补一段 → 修复直接内联进现有函数 → 每段修复自带 `try/except + 日志 + 兜底` 三件套 → 函数越来越长，防御机器越滚越大。

这条链正好解释了为什么仓库把"打补丁"列为第一禁（`AGENTS.md` 反补丁三禁）。补丁不止是逻辑上的隐患，它在物理上就是这 30 万行的来源。

## 治理手段

### 一、防御原语：把样板收敛成一个实现

针对"同一套 `try/except + 日志 + 继续执行` 样板被手抄数百遍"这个具体病灶，仓库引入了上下文管理器：

```
src/core/guarded.py:24    guard(step, *, log=None, level=logging.DEBUG, limit=200)
```

用法：

```python
x = None
with guard("加载导航图", log=_log, level=logging.WARNING):
    x = load_nav_graph(p)
```

它的语义被明确定义为与原内联写法完全一致：异常被吞掉、按级别落一行日志、控制流继续到 `with` 块之后，块内的 `return`/`continue`/`break`/`raise` 语义不变。它不是"新的错误处理框架"，而是同一语义的单一实现。

实测收敛效果：

| 指标 | 数值 | 测量方式 |
|:---|---:|:---|
| `guard()` / `guarded()` 调用点 | 1,147 处 | AST 扫描 `src/` 全量调用 |
| 覆盖文件数 | 341 个 | 含该调用的文件计数 |
| 当前 try 语句总数 | 3,991 个（分布 747 个文件） | AST 扫描 |
| 同期审计基线（2026-10-04） | 5,200 个 try 块 | `audits/规模根因诊断_2026-10-04.md` |

try 从 5,200 降到 3,991，减少约 1,200 处，与 1,147 处 `guard()` 调用量级吻合。这是"用原语替换样板"的直接结果。

### 二、静默吞噬清零

比长函数更危险的是**静默吞噬**：`except: pass` 或 `except Exception: pass` 会把错误彻底吃掉，出问题时连日志都没有。

实测结果：

```
src/ 全部 .py 中，裸 except（无异常类型）数量 = 0
```

零裸 except 意味着没有任何一处异常处理是"不声明类型的全吞"。所有捕获都至少指定了异常类型，或经过 `guard()` 这个统一的、会落日志的原语。

### 三、pre-commit 五道防线

```
.pre-commit-config.yaml
```

| 防线 | 拦截目标 | 实现 |
|:---:|:---|:---|
| 1 | `except Exception: pass` | `python scripts/pre-commit/check_except_pass.py` |
| 2 | SQL 注入风险 | `python scripts/pre-commit/check_sql_injection.py` |
| 3 | `innerHTML` 导致的 XSS 风险 | `python scripts/pre-commit/check_innerHTML.py`（作用于 `.js` / `.html`） |
| 4 | 安全问题 | `bandit`（配置在 `pyproject.toml`） |
| 5 | 重复定义常量/词表 | `python -m pytest tests/test_core/test_duplicate_definition_gate.py -q` |

防线 1 与实测的"零裸 except"是同一件事的两种保障：一个在提交时拦，一个在代码里体现。

**这里有一处需要注意的实现缺口**：防线 1、2、3 引用的 `scripts/pre-commit/` 目录在当前代码树中不存在。也就是说这三道钩子在 `pre-commit install` 后无法执行（会因找不到脚本而报错）。防线 4、5 不依赖该目录，可以正常运行。这个缺口写在此处，供修复。

### 四、常驻静态门禁

除了提交时拦截，还有常驻的测试级门禁（详见第 25 章）：

| 门禁 | 拦截目标 | 判据 |
|:---|:---|:---|
| `tests/test_core/test_static_scope_gate.py` | 局部变量先读后写 | 对 `src/` 跑 ruff，`--select F821,F823`，要求退出码为 0 |
| `tests/test_core/test_duplicate_definition_gate.py` | 常量/词表重复定义 | A 类同文件、B 类跨模块，各配 ratchet 基线 |
| `tests/test_core/test_instruction_contract_gate.py` | 指令契约（真值表、落库边界、极性反转、单一事实源流序） | 15 个用例 |

静态作用域门禁的价值在于它拦的是**运行时必然抛 `UnboundLocalError`** 的那类缺陷——这类问题往往藏在长函数的分支深处，人工审查很难发现，但静态检查能精确命中。

### 五、ratchet 基线：只减不增

重复定义门禁的 B 类判据允许存量放行，存量记录在基线里：

```
tests/test_core/test_duplicate_definition_gate.py:30   _BASELINE_A = frozenset()
tests/test_core/test_duplicate_definition_gate.py:31   _BASELINE_B = frozenset()
```

两个基线当前都是空的。基线的机制是"只减不增"——清理一处就删一项，永远不允许往基线上加。这个机制的作用是让治理**单调推进**：不需要一次清完存量，但不能因为"存量还有"就放任新增。

### 六、事件叙事注释清零

反补丁三禁的第三条针对注释：禁止保留"某日期修复了某问题""第 N 轮修复"这类事件叙事。原因是这类注释会诱导后来者顺着已废弃的分支继续加分支。

规则是：**规则注释只留一行为什么**（目的 + 它防的是哪个既有缺陷），不留事件。

## 设计取舍

**为什么用"语义等价的原语"而不是"更好的错误处理框架"。** `guard()` 的文档串特意声明"语义与原内联 try/except 完全一致"。这是刻意的：如果新原语顺手改变了错误处理语义（例如改成抛新异常、改成聚合上报），那么替换上千处样板就变成一次高风险的行为变更。先做"等价的收敛"，把规模降下来，再谈改进语义——顺序不能反。

**为什么门禁分两层（提交时 + 常驻）。** pre-commit 钩子只在参与者安装了钩子时生效，且可以被 `--no-verify` 跳过；常驻的 pytest 门禁则可以在 CI 或任意一次全量测试运行时执行，无法绕过。两层互补：钩子提供即时反馈，常驻门禁提供不可绕过的事实。

**为什么用 ratchet 而不是一次性清零。** 跨模块的词表统一需要逐个评审（两个模块的"同一词表"可能语义确实不同），一刀切会强迫错误合并。ratchet 允许治理按自己的节奏推进，同时保证方向单调。基线为空说明这个节奏已经走到终点，但机制保留——将来新出现的重复仍然会被拦。

**为什么把规模诊断写成一份独立文档而不是散在提交信息里。** 诊断的结论（"超配 2–3 倍""防御机器占 46%"）是判断后续所有重构优先级的依据。写在提交信息里会被淹没，写成 `audits/` 下的文档才能被反复引用。代价是文档本身也会过期，需要维护。
