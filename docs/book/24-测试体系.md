# 第 24 章　测试体系

## 概述

`tests/` 下按模块分目录组织测试，每个目录对应一处被测面。实测为 14 个子目录加 2 个顶层验收文件，合计 16 组（契约表称"16 组"，与纯目录数 14 的差异由顶层文件补足）。目录下共有 301 个以 `test_` 命名的测试函数，分布在 41 个 `.py` 文件中（统计用 AST 遍历 `tests/`，`__init__.py` 不计）。

运行入口由 `pytest.ini` 统一控制：`testpaths = tests`、`junit_family = xunit2`、`addopts = -ra --strict-markers`（见 `pytest.ini:4,10`）。`markers` 定义了 `asyncio / unit / integration / e2e / security / slow`（见 `pytest.ini:11-17`），但实测全仓测试函数均未使用任何 `@pytest.mark`，目录驱动为 CI 实际方式（见 `pytest.ini:6-8` 注释）。

## 链式回归：金样本机制

`tests/test_chains/test_cross_cut_lifecycle.py` 用真实编排器走完整链，只在网络边界外全真（见 `tests/test_chains/test_cross_cut_lifecycle.py:1-16`）。4 个用例覆盖：

- `test_c4b_c6_c7_api_demo_full_lifecycle`：断言功能探针（C4b）、authz 横切打到存活 SUT（C6）、报告落盘且 `all_pass`（C7）三链不变量（`:38-79`）。
- `test_c7_report_file_is_wellformed_json`：报告为可解析 JSON（`:82-88`）。
- `test_c4b_c6_c7_golden_lane_structure`：将本次产物用 `_normalize` 归一化（数字替换为 `0`）后与 `golden/api_demo_lane.json` 逐字段比对，结构漂移即红（`test_cross_cut_lifecycle.py:122-134`）。
- `test_c4a_browser_lane_spa_demo_lifecycle_and_golden`：SPA 浏览器道（C4a）走真 Chromium，断言横切四维 `a11y/perf/security/visual` 齐活并与 `golden/spa_demo_lane.json` 一致（`test_cross_cut_lifecycle.py:160-177`）。

金样本基线存于 `tests/test_chains/golden/`（`api_demo_lane.json`、`spa_demo_lane.json`）。机制要点：上一条用例断言"对不对"，金样本用例断言"形状没变"，任何重构导致结构漂移都会显式暴露；有意变更时更新 golden 文件即可（基线只许有意变更，见 `test_cross_cut_lifecycle.py:123-134` 注释）。运行条件为本机引擎 MySQL 可达加 `api_demo` 靶子依赖（`:15`）。

## 覆盖的风险面

- 流水线单点：Step1 信号（隐式）至 Step5 报告补测，每组覆盖一个阶段；`test_step3`/`test_step4`/`test_step5` 直接对应步骤。
- 横切质量：a11y（`test_a11y`）、性能（`test_perf`）、预言机/置信度（`test_oracle`）、接口轨（`test_api`）。
- 工程纪律：门禁（`test_core`）、配置加载（`test_config_loader`）、权限模型（`test_users`）、前端硬约束（`test_frontend`）。
- 链路级：生命周期顺序缺陷（`test_chains`），组件单测互不衔接时只有它能抓（见 `:4-8` 背景）。

## 设计取舍

- 按模块分目录而非单文件平铺：目录即被测面索引，新增能力时测试落点确定。
- 金样本比对将"结构"与"正确性"分离为两条用例，避免重构噪声淹没真实回归。
- 全仓未使用 marker 分层，CI 改为目录驱动；代价是 `-m unit` 等过滤在当前快照下命中 0 条（见 `pytest.ini:6-8`）。
