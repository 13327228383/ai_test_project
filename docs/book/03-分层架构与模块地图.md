# 第 3 章　分层架构与模块地图

## 概述

本章给出代码的全局地图。`src/` 下分 18 个一级包，共 1,163 个 Python 文件、约 29.2 万行（按 AST 索引统计的文件行数，脚本见 `docs/book/_build/gen_file_index.py`）。这个规模不是均匀分布的：`pipeline` 一个包就占了 60% 的行数。

## 五个逻辑层

代码按职责分成五个逻辑层。这个划分不是物理目录划分（目录按功能组织），而是依赖方向上的分层。

| 层 | 核心对象 | 职责 | 主要落点 |
|:---|:---|:---|:---|
| 资产层 | `TestCase {case_id, actions, checks}` | 系统的唯一测试资产格式 | `test_cases` / `case_meta` 表 |
| 策略层 | 策略路由函数 | 按数据完整度选执行策略 | `pipeline/steps/step4/strategy_router.py` |
| 执行层 | 浏览器 / 接口 / 数据库执行器 | 真正驱动被测系统 | `pipeline/steps/step4/`、`api_only_executor.py` |
| 验证层 | 检查点判定与终判 | 把多轨结果归一为结论 | `pipeline/steps/step4/verification/` |
| 报告层 | 报告与补测建议 | 汇总、算通过率、出建议 | `pipeline/steps/step5/` |

依赖方向是自上而下的：报告层读执行结果，执行层读策略，策略读资产。反向依赖（执行层回头改资产格式）被禁止——这是保持口径统一的物理前提。

## 依赖方向原则

从 `pipeline/utils`（96 个文件的共享工具层）的存在可以看出一个隐含约定：**跨步共享的逻辑优先下沉到 `utils`，而不是让后面的步骤 import 前面的步骤。** 它们主要通过数据库表和 `utils` 里的存储层交互。

**★ 实测更正（2026-10-15）：这条约定不是硬约束，存在 19 处跨步 import。** 对 `src/pipeline/steps/stepN/` 下全部 417 个 `.py` 做 AST import 统计，结果为：`step3 → step4` 10 处、`step5 → step4` 6 处、`step4 → step3` 2 处、`step2 → step4` 1 处。即：

- **Step5 确实 import Step4**（6 处），本章上一版写的"Step5 不 import `step4_executor`"不成立；
- `step3 ↔ step4` 双向引用，Step4 是被 step2/step3/step5 共同依赖的**共享下游**；
- 真正被守住的方向是"**`utils` 不反向 import 上层步骤**"——这一条实测无反例。

因此本节标题所称的"原则"应理解为**倾向性约定**而非强制约束：跨步引用集中在 step4 这一个方向上，尚未形成环形依赖，但也没有门禁在拦它。

这个约定的收益是步骤可以独立触发与独立测试（Web 控制台允许单独执行某一步）。代价是数据一致性要靠表结构保证，而不是靠函数返回值——这也是为什么数据表多达 90 张。

## 设计取舍

**为什么 `pipeline` 没有进一步拆包。** `pipeline` 有 616 个文件、17.5 万行，把它拆成三个包（步骤、执行、工具）在结构上更清晰。不拆的理由是：拆分会让大量相对导入变成绝对导入的跨包路径，改动面覆盖上千个文件，风险高于收益。取而代之的做法是**在包内用目录切分**（`steps/step1`–`steps/step5`、`utils`、`fetchers`、`plugins`），并用门禁（第 25 章）防止目录间出现循环依赖。

**为什么把 `agent` 独立成包。** `agent` 只有 10 个文件，却有 8,170 行——平均每个文件 817 行，是全仓最"厚"的包。它被独立出来，是因为浏览器探索智能体的职责与流水线步骤不同：步骤是"编排"，智能体是"决策"。保持独立让它的改动不会波及步骤层。代价是 `_action.py` 这样一个 4,284 行的单文件长期存在，见第 15 章。

**为什么 `extensions` 的粒度差异这么大。** `rag_engine` 31 个文件、`security_scanner` 只有 1 个文件（790 行）。粒度不均是演进的自然结果：检索逻辑复杂，需要分块、嵌入、检索、重排多个阶段；安全扫描是一组正则规则，单文件足够。强制统一粒度会制造空目录。
