# 第 27 章　诊断与运维工具

## 概述

运维能力分布在两处：`scripts/`（33 个顶层 `.py` 加 `audit/bundle/case_runner/maintenance` 四个子目录）承担验收驱动、审计、数据修复、打包、用例批量执行等运维动作；`src/pipeline/diagnostics/` 与 `src/pipeline/evidence/` 是引擎内置的诊断与证据模块，帮助在失败发生时定位根因。

说明：顶层脚本与子目录脚本普遍无模块 docstring，下列"职责"依据文件名语义归纳，精确行为以「待核实」标注。

## 诊断模块：src/pipeline/diagnostics/

`src/pipeline/diagnostics/__init__.py` 定义"诊断中心"职责为流水线自检 + 失败归因 + Step 健康快照。核心文件 `self_test.py`（约 17.7 KB）：

- `run_self_test(project, ...)`（`self_test.py:33`）逐 Step 独立自检，单步失败不阻断后续；Step2 实际拆解内置需求（验证 AI + 规则引擎），Step3/4/5 检查基础设施（AI Brain/DB/浏览器/报告表），单次自检 < 30 秒（见 `self_test.py:1-23` 与 `:60` 起各 `_check_stepN`）。
- 结果写入 `pipeline_self_test_results` 表（`:18-23` 注释）。
- 后端经 `src/backend/routes/diagnostics/diagnostics_api.py:28,52,70` 调用 `run_self_test`/`get_latest_self_test`/`get_self_test_history`，提供 HTTP 诊断接口。

## 证据模块：src/pipeline/evidence/

`evidence/__init__.py` 定义"证据引擎"：AI 不做裁判，只做证据收集器；置信度 = 独立证据验证 + 历史实证校准 + 贝叶斯后验。两个文件：

- `calibration.py`（约 13.3 KB）：`record_calibration()`（Step4 后批量写校准）、`get_calibration()`（读历史准确率）、`_bayesian_posterior()`（Beta-Binomial 共轭）。校准维度白名单 `CALIBRATION_DIMENSIONS`（`consensus_level/perspective_count/source_quote/requirement_type/risk_level/case_type`，`calibration.py:30-41`）。
- `confidence.py`（约 15.2 KB）：`compute_evidence_confidence` 将 AI 自评升级为证据驱动置信度，权重 `0.40 证据 + 0.35 校准 + 0.15 抽取质量 + 0.10 schema 校验`（`confidence.py:24-28`），支持冷启动降权与配置覆盖（`_get_default_weights`，`:42` 起）。

证据模块帮助定位"假绿/假 FAIL"：低校准维度（如某 `requirement_type` 历史准确率低）直接暴露判定不可信的来源，供第 32 章误判根因库使用。

## 一致性检查器：src/pipeline/utils/consistency_checker/

流水线的一致性检查器（`src/pipeline/utils/consistency_checker/__init__.py`），包文档串（`:5-8`）明确其定位：**只做只读检查，不修改 Excel/MySQL/任何过程产物**，用途是把"事实源混合"（Excel 与 MySQL 双事实源）带来的脏数据风险提前暴露，避免错误流入执行与报告。

- **三项检查**：`run_all_checks(excel_handler, tracker)`（`:53`）聚合三项——`check_mysql_environment`（`env.py`）、`check_intent_mapping_consistency`（`mapping.py`）、`check_intent_executability`（`executability.py`），返回 `{ok, checks, summary{error_count, warning_count}}`。
- **阶段钩子**：`run_and_print_checks(stage)`（`src/pipeline/utils/consistency_checker/__init__.py:82`）是非阻断包装（异常降级为 info 日志），在流水线三个边界被调用：Step3 收尾（`step3/__init__.py:604`）、Step4 执行编排（`step4_executor.py:704`）、Step5 报告前（`steps/step5/report_generator.py:71`）。
- **迁移健康**：`migration.py` 的 `check_mysql_migration_health` 检查事实源从 Excel 迁移到 MySQL 的健康度；`printer.py` 提供 `print_check_report` / `print_repair_plan`。
- **修复计划（只读优先）**：`build_intent_mapping_repair_plan`（`mapping.py`）产出修复计划；真正写库的 `apply_stale_mapping_repair`（删 Excel 已不存在的残留映射）与 `apply_safe_missing_mapping_repair`（补 Excel 显式 `req_id` 的安全缺失映射）默认 dry-run，需 `--yes` 才执行（`__init__.py:180-200`）。这些写操作实现在 `consistency_helpers`（`__init__.py:18-30`），与只读检查物理分离。
- **CLI**：`main()`（`:105`）提供 `--stage`/`--json`/`--repair-plan`/`--mysql-health`/`--sync-excel-to-mysql`/`--export-*`/`--import-trace-links-json`/`--strict` 等子命令；默认即使发现 error 也返回 0（便于观察现状），加 `--strict` 后存在 error 才返回 1，供 CI 接入（`:110-113`）。

## 设计取舍

- 诊断与证据下沉为引擎内置模块（`diagnostics`/`evidence`），使失败归因可在运行时经 HTTP 接口即时获取，而非依赖离线脚本。
- 运维脚本以文件名分区（diag_ 诊断、_verify_ 一次性验收），前缀即生命周期标注，降低误用长期工具执行临时脚本的风险。
- 证据模块与门禁（第 25 章）互补：门禁防"提交时"的结构性缺陷，证据模块防"运行时"的置信度失真。
