# 第 32 章　关键设计五 · 误判根因库

## 概述

测试引擎最危险的失效不是"跑不起来"，而是**跑起来了但结论是假的**。跑不起来会被立刻发现，假结论会被当成事实交给下游——报告上写着"全部通过"，或者写着"产品有缺陷"，而两者都可能与真相不符。

本章整理这套引擎在四类误判上留下的机制与守卫。每一类都给出失效的形态、判据所在的代码位置、以及当初为什么会这样设计。这些机制不是抽象规范，而是针对具体失效逐一建立的。

## 误判一：假 PASS

假 PASS 指用例实际没有验证到任何东西，却被记为通过。它有四个来源，对应四道守卫。

**来源 1：没有断言也记通过。** 用例的 `checks` 为空，执行器"顺利跑完"就记 PASS。守卫是全仓唯一的断言缺失判据：

```
src/pipeline/utils/validation.py:22   is_no_valid_assertion(case) -> bool
```

命中条件包括：用例为空或非字典、`total_assertions == 0`、`checks` 为空列表。它的文档串明确写着"全仓唯一判定，禁止双重实现"（`src/extensions/confidence_calculator_mixins/_calculate.py:109` 也重复了这一约束）。

**来源 2：置信度不足也记通过。** 断言执行了，但判定证据薄弱。守卫在终判函数里。

**来源 3：有的轨没验证却记通过。** 用例声明了三轨校验，其中一轨根本没有产生结论（UNKNOWN），整体仍记通过。

**来源 4：置信度缺失（空值）被当作"没问题"。**

来源 2、3、4 集中在同一个函数里解决。

### PASS 判定的唯一入口

`src/pipeline/steps/step4/verification/verdict.py` 的模块文档写着一句话：**全仓唯一一处决定用例最终 verdict 的函数。** 它处理的正是历史上"多条路径各自判定 PASS 导致同一用例结论不同"的问题。判定规则是五条，按顺序：

| 序 | 条件 | 结果 |
|:---:|:---|:---|
| 1 | `status != PASS` | 维持原状态（FAIL / MANUAL_REVIEW 不被二次改判） |
| 2 | `status == PASS` 但任一轨 UNKNOWN | 降级 UNKNOWN（未验证不得通过） |
| 3 | `status == PASS` 但置信度缺失（None） | UNKNOWN（无置信度不判 PASS） |
| 4 | `status == PASS` 但置信度 < 阈值 | FAIL（假 PASS 拦截） |
| 5 | 全轨非 UNKNOWN 且置信度 ≥ 阈值 | PASS |

阈值是代码常量：

```
CONFIDENCE_THRESHOLD = 0.70     # src/pipeline/steps/step4/verification/verdict.py:28
```

它的注释写着"配置可上调不可下调"。这个方向性约束很重要：阈值下调等于放宽假 PASS 的拦截，属于降低标准的操作，不允许通过配置静默发生。

结论枚举只有三个值：`VERDICT_PASS` / `VERDICT_FAIL` / `VERDICT_UNKNOWN`（`verdict.py:31-33`）。注意这里没有 SKIP 和 ERROR——终判只回答"这条断言算不算过"，"为什么没过"由另一层（失败归类）回答。

## 误判二：假 FAIL 与假 Bug

这是危害最大的一类：报告说"被测系统有缺陷"，而实际是引擎自己的问题。它会直接误导修复方向，让开发人员去改一个没坏的模块。

### 形态：把引擎缺口算成产品缺陷，或反之

两个方向的误判都发生过：

- **把产品缺陷算成引擎错误。** 用例里同时有"能执行的断言"和"引擎不支持的断言"，前者真实失败（例如移动端布局重叠 44 像素、可访问性违规 10 处），后者是引擎尚未实现的检查类型。旧实现只要 `checks` 里出现任何一个不支持的类型，整条用例就被归为 `HARNESS_ERROR`（引擎错误）。结果是真实的产品缺陷被归进"执行异常"，系统性低估产品问题。
- **把引擎问题算成产品缺陷。** 修完上一个问题后，判据改成"只看 `checks` 里失败项的 reason 是否是 `UNSUPPORTED_CHECK`"，但这套 reason 白名单漏掉了另外两类引擎侧失败（轨道级失败、以及状态为"不适用"的跳过项），于是它们被兜底判成 `PRODUCT_BUG`，产出假 Bug。

### 守卫：按"真正执行过的断言"归类

修复后的判据在 `src/pipeline/steps/step4/browser_core/single_mixins/_agent_checks.py` 的 `_classify_checks_failure`（`:65`）。归类逻辑：

| 条件 | 归类 | 状态 |
|:---|:---|:---|
| 存在**已执行且失败**的断言 | `PRODUCT_BUG` | FAIL |
| 失败完全由引擎不支持的检查类型造成（无任何已执行失败项） | `HARNESS_ERROR` | ERROR |
| 超时、网络错误 | `ENVIRONMENT_ERROR` | ERROR |

判定优先级是刻意的：**"已执行且失败"优先于"存在未支持的检查"**。理由是前者是产品行为的直接证据，后者只是引擎能力边界，不能因为边界的存在就否认可执行部分的证据。

### 关键实现细节：不维护本地白名单

归类函数自己不判断"什么算失败"，而是调用结构化权威：

```
src/pipeline/steps/step4/verification/_track_protocol.py   is_negative_verdict(check)
```

代码注释写明了不这么做的代价：本地的 reason 白名单"只看 reason、漏了 skipped/status，会把引擎自述'不适用'的项当成失败"。这是第 31 章"语义唯一源"原则的一次具体应用——判负语义只有一个实现，归类函数只读不推。

## 误判三：异常 SKIP

SKIP 表示"这条用例没跑"。它本身不是错误，但**没有归因的 SKIP 是**——它把"为什么没跑"这个问题藏了起来，让通过率显得比实际干净。

这套引擎的处理是：SKIP 必须带原因，且原因要能区分是谁的问题。

| SKIP 形态 | 归因 | 判据位置 |
|:---|:---|:---|
| 所有轨都被跳过 | 全跳过 | `src/pipeline/steps/step4/verification/_track_protocol.py:287` |
| 只有"无判定"结果，没有有效断言 | `no_valid_assertion` | `browser_core/single_mixins/_agent_checks.py:702`（`no_verdict_only`） |
| 数据库轨结果未验证 | 归 FAIL（不是 SKIP） | `verification/_db_ui.py:174-178` |

第三行值得注意：DB 轨的"未验证"被判为 **FAIL 而不是 SKIP**。理由是数据校验声明了却没验证，等于没有证据支持"数据正确"，不能按"跳过"放过。

## 误判四：ERROR 的归因

ERROR 表示执行过程出错。它必须区分"引擎没这个能力"和"执行器崩了"。

| 来源 | 标识 | 位置 |
|:---|:---|:---|
| 检查类型未注册（词表漂移） | `UNSUPPORTED_CHECK` | 生成侧守卫 `src/pipeline/step3/_check_guard.py:396-415`；执行侧记 ERROR |
| 执行器抛异常 | `EXECUTOR_EXCEPTION` | `src/pipeline/steps/step4/browser_core/single_mixins/_assertion_verdict.py:85` |
| 断言分派异常 | 摘要含"分派异常" | `_agent_checks.py:104-105` |

### 词表漂移的成因与守卫

`UNSUPPORTED_CHECK` 的典型成因是**词表漂移**：生成端发射了一个检查点类型，执行端的注册表里没有这个类型。生成端以为执行端认识它，执行端遇到它只能报"不支持"。

守卫在生成侧：`src/pipeline/step3/_check_guard.py` 的 `_build_executable_check_types`（`:49`）从执行端注册表投影出可执行类型清单，生成时校验（调用点 `:74`），不匹配的类型被剔除（`:396-415`），并落一条漂移日志（`:405`）。执行端的权威注册表是 `src/pipeline/steps/step4/verification/_db_ui.py:2870` 的 `_UI_CHECK_DISPATCH`。

处理这类问题的原则是**补执行器或补词表映射，不放宽守卫**。放宽守卫（例如"不认识就跳过"）只会让漂移继续存在，且从"报错"退化成"静默不测"——比报错更糟。

这个状态集合刻意不收敛成两值。把"没跑"、"跑了不过"、"引擎不会"、"环境坏了"混在一起，会让报告失去归因能力。

## 报告口径

通过率的分母不是"全部用例"。`src/pipeline/steps/step5/report_generator.py` 里的判定：

```
_is_executed = {PASS, FAIL, SKIP}                     # :86-88
_is_blocked  = {BLOCKED, PRE_GATE_BLOCKED}            # :92-94
blocked = 计数(_is_blocked)                            # :100
pending = 计数(非 executed 且非 blocked)               # :101
```

`SKIP` 计入分母（它属于 `_is_executed`），`ERROR` 与 `FLAKY` 不计入（落入 pending）。这个口径的含义是：跑过但跳过的算进分母，这是诚实的做法——跳过不应当提高通过率；而"引擎不会"和"环境坏了"不算，因为它们反映的是引擎与环境的状态，不是被测系统的质量。

## 设计取舍

**为什么 PASS 判定要独立成一个函数。** 多处判定会分叉：计划期硬编码一处、门禁一处、评分卡一处、证据引擎一处，同一个用例在不同路径得出不同结论。收敛成单函数后，真值表可以用单测穷举（3 状态 × 3 轨 × 置信度边界）。代价是所有判定路径都必须经过它，绕开它就等于绕开整个防线——所以门禁（第 25 章）会检查这类唯一性约定。

**为什么阈值是代码常量而不是纯配置。** 配置化的阈值可以被现场改成 0.5，假 PASS 的拦截就失效了。写成代码常量 + "可上调不可下调"的契约，把降低标准的操作挡在配置之外。

**为什么"已执行失败"优先于"存在未支持检查"。** 归类必须反映"有多少证据"。一条用例里有 3 个断言失败、1 个类型不支持，正确结论是"产品有问题"，而不是"引擎不会"。若按后者归类，真实缺陷会被引擎的能力缺口掩盖——这类掩盖在报告里看不出来，危害比误报更大。

**为什么 ERROR 与 SKIP 不合并。** 合并会丢掉归因：测试人员看到"SKIP"会去查前置条件或环境；看到"ERROR"会去查引擎日志或能力缺口。两者指向完全不同的排查路径。
