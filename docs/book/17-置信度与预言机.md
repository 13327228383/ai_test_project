# 第 17 章　置信度与预言机

## 概述

本章覆盖：置信度计算（`src/extensions/confidence_calculator_mixins/`）、差异引擎（`src/extensions/diff_engine/`）、追溯校验器（`src/extensions/trace_validator/`）、预言机（`src/oracle/`）、验证台账（`src/verification/`）。

前三者回答"引擎这次判定有多可信、改了什么、用例里写的表/接口是不是真的存在"；后两者回答"有没有独立真值去兜底断言、引擎自己的预测到底对不对"。

## 置信度计算（`confidence_calculator_mixins`）

`ConfidenceCalculatorCalculateMixin._calculate`（`src/extensions/confidence_calculator_mixins/_calculate.py:80`）计算单条用例置信度，是 Step5 报告与补测建议的核心输入。

### 维度与权重

置信度由六个因子加权求和（`_calculate.py:431`）：

| 因子 | 配置项 | 默认值 |
|:---|:---|---:|
| assertion_rate（断言通过率） | `CONFIDENCE_WEIGHT_ASSERTION` | 0.30 |
| case_completeness（用例完整度） | `CONFIDENCE_WEIGHT_STRUCTURED` | 0.20 |
| hard_verify_rate（硬验证通过率） | `CONFIDENCE_WEIGHT_HARD_VERIFY` | 0.18 |
| first_try_rate（首次尝试成功率） | `CONFIDENCE_WEIGHT_FIRST_TRY` | 0.15 |
| semantic_align（需求-用例语义对齐） | `CONFIDENCE_WEIGHT_SEMANTIC` | 0.12 |
| cache_hit_rate（经验复用命中率） | `CONFIDENCE_WEIGHT_CACHE` | 0.05 |

权重来自 `pipeline_config`（`pipeline_config.py:396`），可通过环境变量覆盖。`_calculate.py` 顶部 docstring 写的是 0.35/0.25/0.20/0.15/0.05 的旧设计值，与当前默认值不一致（见「待核实」）。

构造时做权重和校验：六项之和必须 == 1.0（±0.001），否则抛 `RuntimeError` 拒绝启动（`_calculate.py:51`）。这是"0.70 阈值要成立，被比较的数本身必须稳定"的根因修复——置信度分母不稳定会导致同一用例跨环境得不同分（`_calculate.py:46`）。

### 关键规则

- 无有效断言（零断言）时 `confidence` 直接置 0.0，不进入加权（`_calculate.py:114`），修复了"零断言用例反算 ≈0.740 照样过闸"的缺陷（`_calculate.py:107`）。
- 三轨 checks 证据（`_verify_result.ui/api/db`）在 `verified==True` 时计入断言率，缺失 `verified` 字段的轨默认跳过（`_calculate.py:192`），fail-safe 防止新靶子虚假证据抬高分数。
- 分层阈值在 `_block.py`：`LOW_CONFIDENCE_THRESHOLD=0.50`、`MEDIUM_CONFIDENCE_THRESHOLD=0.70`、`HIGH_CONFIDENCE_THRESHOLD=0.90`（`_block.py:19-27`，默认值来自 `confidence_low/medium/high_threshold`）。`_calculate.py:436` 据此给结论：`>=0.90` 高/自动通过，`>=0.70` 中/建议复核，`<0.70` 低/需人工确认；未通过的用例置信度封顶 0.69（`_calculate.py:447`）。

### 0.70 阈值的来源

0.70 不是数学推导值，而是 `confidence_medium_threshold` 配置的策略常量（默认 0.70），由 `_block.py` 读取。其约束条件来自权重和校验——只有被比较的置信度自身稳定，0.70 才有意义。它不是"经验拟合最优分界"，而是可配置的质量门禁中点。

## 差异引擎（`diff_engine`）

`DiffEngine`（`src/extensions/diff_engine/engine.py:16`）做多维度数据对比，快照统一落 MySQL `diff_snapshots`（`engine.py:17`）。它比对三类对象：

- `diff_requirements`（`engine.py:61`）：按 `req_id` 做新增/删除/修改判定，首次运行全为 added。
- `diff_api_schema`（`engine.py:152`）：按 `METHOD:path` 键比对接口新增/删除/字段变更（title/req_params/res_body）。
- `diff_db_schema`（`engine.py:220`）：按表比对新增/删除，按列比对增删列。

三类报告的变更条目统一为 `DiffEntry`（实体类型 + 变更类型 + 新旧值），由 `DiffReport`（`models.py`）汇总 added/removed/modified 计数。`change_impact_kb` 的"变更信号"正来自这里的 diff 结果。

## 追溯校验器（`trace_validator`）

`TraceValidator`（`src/extensions/trace_validator/__init__.py:27`）解决"防幻觉"问题：校验测试用例里的 `db_checks`/`api_checks` 引用的表名、API 路径是否真实存在于追溯链路 `trace_links` 中。

校验入口 `validate_intent`（`__init__.py:107`）从用例步骤抽取 `db_checks`/`api_checks`，`_validate_db_checks` 校验表名与字段名是否在 schema 中，`_validate_api_checks` 校验 API 路径；找不到时走 `fuzzy_match` 模糊匹配，给出 issue 或 warning。适配器 `validate_checks_against_trace`（`__init__.py:230`）只校验 `precision=exact` 的检查项，fuzzy 检查不要求精确表名（`__init__.py:312`）。它从 `db_checks.py`/`api_extractors.py`/`fuzzy_match.py` 三个 mixin 聚合而成。

## 预言机（`src/oracle`）

`src/oracle/` 提供"预言机（oracle）"——替代或增强断言的独立真值判定源。

`VLMOracle.check(layout_spec, screenshot, dom_summary)`（`src/oracle/correctness_vlm.py:72`）是视觉预言机：用 VLM 对比"期望布局"与"实际截图"，返回 `{match, diff_regions, grounding, confidence, reason}`。`match` 为 `true/false/null`（null=无法判定），provider 不可用时降级为 `confidence=0`、`match=None` 不阻断流水线（`correctness_vlm.py:103`）。底层 provider 默认 Ollama，模型 `qwen2.5vl:3b`，图像最长边缩放到 768 像素（`src/oracle/vlm_adapter.py:33,39`），通过 `/api/chat` 调用（`vlm_adapter.py:183`）。

预言机与 `check` 判定的关系：`steps/step4/verification/` 下的 `check`/`verify_*` 是"引擎执行期对单一断言的判定"（如元素存在、文本包含、状态码匹配）；预言机是"脱离执行脚本的独立视觉真值源"，专门补上视觉断言难以量化的"布局是否真的符合预期"这一环（如柱子是否遮挡坐标轴）。二者是增强与被增强关系，预言机结论经 `src/oracle/store.py` 写入 `oracle_results` 与 `visual_review` 表（`store.py:34,140`），作为执行证据留存。

## 验证台账（`src/verification`）

`src/verification/` 是一套"验证台账/补做闭环"，职责与 `steps/step4/verification/` 完全不同，容易混淆：

- `steps/step4/verification/`（`src/pipeline/steps/step4/verification/`，含 `_verify_*.py`、`verdict.py`、`tracks.py`）是执行期的三轨断言库——回答"这条用例过没过"。
- `src/verification/` 是执行后的"引擎准确性台账"——回答"引擎的预期到底对不对"，只有 8 个文件：`schema.py`（数据模型）、`runner.py`（比对闭环）、`ledger_store.py`、`aggregate.py`、`remediation.py`、`hooks.py`、`cli.py`、`meta/`。

`LedgerRecord`（`src/verification/schema.py:102`）记录 `target`/`case_id`/`engine_expected`/`truth_value`/`consistent`/`status`/`disposition`/`truth_source` 等字段，pydantic 校验枚举值（`schema.py:136`）。`VerificationRunner`（`src/verification/runner.py:54`）三阶段运行：

1. `write_engine_expected`（`runner.py:74`）写入引擎预测，`consistent` 初值 `truth_unavailable`；
2. `compare`（`runner.py:117`）读取独立真值（来自靶子 `spec.md` 解析 `parse_spec_truth`，`runner.py:312`，或人工标注），逐字段比对 `_is_consistent`（`runner.py:187`），一致→closed、不一致→open（经 `RemediationStateMachine`）、真值缺失→`truth_unavailable` 绝不静默通过；
3. `advance`（`runner.py:221`）驱动 `open→fixing→recheck→closed` 补做状态机，`known_limitation` 关闭需审批人。

台账以 JSONL 落盘在 `src/verification/ledger/`，已存在 `authz_sut.jsonl`/`hospital_sut.jsonl`/`shop.jsonl` 三份数据，说明该模块已实际写入（`ledger_store.py`）。`aggregate.py` 的 `aggregate_ledger_summary` 被 `backend/routes/kpi/_aggregator.py:44` 调用产出准确性汇总。

## 设计取舍

- **权重和硬校验**：把"置信度可比性"前置到构造期，牺牲少量启动开销换跨环境结论稳定，这是 0.70 阈值可信的前提。
- **预言机降级不阻断**：VLM 不可用时 `match=None`/`confidence=0`，让视觉校验在缺少 Ollama 时退化为"不参与"，而非报错中断流水线。
- **验证台账与执行断言分离**：`src/verification/` 不直接依赖 `pipeline/empirical`，只依赖本模块 + 靶子 `target_cfgs`，使"引擎自测准确性"成为可独立运行、CI 可消费的闭环。
