# 第 0 章　前言：这本书是怎么写成的

## 这本书回答什么问题

E2E 智能测试引擎是一套用 AI 驱动端到端测试的系统：读需求文档，拆成结构化需求，生成测试用例，在真实浏览器里执行，最后出报告。它的代码量是 `src/` 下 1,163 个 Python 文件、约 29 万行，另有靶子系统、测试套件、运维脚本合计 1,322 个 Python 文件。

代码本身不缺。缺的是"为什么是这样"。

一个刚接手的人打开 `src/`，会看到 616 个文件的 `pipeline` 目录、188 个文件的 `backend` 目录、176 个文件的 `extensions` 目录，以及 90 张数据库表。他能知道每个文件叫什么，但很难知道：

- 为什么断言的"精度"被抽象成一个字段，而不是按接口轨、界面轨、数据轨各写一套判定；
- 为什么需求拆解要按 600 字切片；
- 为什么同一个语义（比如"期望报错"和"期望成功"的极性判定）不允许在两个地方各写一遍；
- 为什么执行结果表里同时存在 PASS、FAIL、SKIP、ERROR、BLOCKED 五种状态，而不是简单的通过/不通过。

这本书逐个模块回答这些问题。它不替代代码，而是给代码补上一层"设计意图 + 代价 + 落点"的说明。

## 怎么写成的

写作过程分三步，每一步都可复核。

**第一步，机械索引。** 用一个 AST 脚本扫描仓库内全部 Python 文件，提取每个模块的文档串、顶层类及其方法数、顶层函数签名、以及模块间的内部依赖，输出为 `docs/book/_build/file_index.json`。这一步保证附录 A 的文件清单不靠人工列举，不会漏。脚本在 `docs/book/_build/gen_file_index.py`。

**第二步，逐模块精读。** 按目录划分阅读单元，每个单元读完后写出对应章节，正文里的机制性结论都要求能落到 `文件路径:行号` 或明确的符号名。

**第三步，分歧核实。** 阅读中凡遇到代码与既有文档不一致的地方（例如某处文档说表有 94 张、实际建表语句只有 90 张），一律回到代码重新确认，以代码为准，并在正文中写出差异。

## 事实分级

这本书对每一条结论标注了它属于哪一种事实，读者可以据此判断可信度：

- **代码事实**：直接读代码得到，例如"终判函数 `decide_verdict` 在置信度低于 0.70 时不判通过"。这类结论在章末的"本章代码依据"里列出文件与行号。
- **实测结果**：由脚本或 SQL 实际运行得到，例如"`schema.sql` 中真实的建表语句有 90 条"。正文会写明测量方法与工具。
- **待核实**：阅读中无法确认、或存在相互矛盾的地方，统一放在每章末尾的"待核实"小节，并给出核实方法。正文里不出现"应该是""大概是"这类推断式表述。

这个分级是有代价的：它让部分章节显得不够"完整"。例如某个模块是否真的被调用，如果一次阅读无法追清全链路，书里会留一条待核实，而不是给一个听起来顺耳的答案。测试工具这一类软件的说明文档，最不能容忍的就是把推断当结论——读者照着一句错误的话去改代码，代价由他承担。

## 写作约定

**术语统一。** 全书使用同一套术语，旧名与新名的对应关系集中在附录 D。几个高频词的约定如下：

- **用例（TestCase）**：`{case_id, actions, checks}` 结构体，是系统的核心测试资产。
- **动作（actions）**：结构化操作序列，例如"点击登录按钮"。
- **检查点（check）**：结构化验证点，形如 `{track, precision, check, expect}`。
- **轨（track）**：检查点所属的执行通道，取值为 ui、api、db 三者之一。
- **精度（precision）**：检查点的判定方式，取值为 exact（规则判定）或 fuzzy（AI 辅助判定）。

**代码引用格式。** 正文引用代码位置时写作 `文件路径:行号`，路径相对仓库根目录。提及函数或常量时使用反引号包裹原名。

**图示。** 流程与结构优先用表格或 ASCII 图表示，避免依赖外部渲染。

**数字。** 所有数字都来自本次实测，并注明来源（脚本名、SQL 或 `wc`）。不做估算。

## 读者需要什么基础

读第二篇（流水线）和第四篇（控制台）需要熟悉 Python 与 Flask。读第三篇（横切能力）需要了解 Playwright、MySQL 与基本的向量检索概念。第一篇、第五篇、第六篇、第七篇不要求特定技术栈背景，只要求具备软件测试或后端开发的常识。

## 一处诚实的说明

这套引擎的能力边界，书里写得很清楚：哪些部分是确定性的规则实现，哪些部分真的调用了大模型。这个区分对理解系统的可靠性至关重要——一个"看起来智能"的功能如果实际是规则拼出来的，那么它在遇到规则没覆盖的场景时不会自己想办法。凡涉及这一点的地方，本书都会指明该功能由哪条路径实现，以及证据在代码的哪一行。
