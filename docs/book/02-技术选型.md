# 第 2 章　技术选型

## 概述

这一章说明引擎用了哪些技术、为什么用它们、以及依赖清单的真实状态。所有引用次数由 AST 脚本扫描 `src/` 下 1,163 个 Python 文件的 import 语句统计得到，不是估算。

选型的整体倾向是**收敛依赖、集中控制**：能用标准库和自己写的组件解决的，不引入第三方；必须引入的（浏览器自动化、数据库驱动、大模型客户端），把它包在一个薄层后面，让上层只依赖这个薄层。

## 语言与运行时

**Python 3。** 引擎全部代码是 Python，没有混入其它语言编写的核心逻辑（前端的独立日志面板除外，见第 20 章）。

**单进程。** 后端是一个单进程 Flask 应用，通过线程池和信号量控制并发，不依赖 Celery 之类的分布式任务队列。执行并发由执行槽位（run-slot）限制。这个选择的代价是横向扩展能力有限，收益是部署简单——一个进程、一个数据库、一份配置即可运行，适合单机验收场景。

## Web 框架与服务化

| 用途 | 选型 | 引用次数 | 说明 |
|:---|:---|---:|:---|
| HTTP 框架 | Flask ≥ 3.0 | 145 | 全部路由以蓝图（Blueprint）组织 |
| 页面渲染 | Jinja2（Flask 内置） | — | 服务端模板，见第 20 章 |
| 生产 WSGI 服务器 | waitress | 1 | 替代 Flask 开发服务器 |
| 会话持久化 | flask-session | 1 | 会话落 MySQL `flask_sessions` 表 |
| 服务器推送 | SSE（自实现） | — | 实时日志经 `RingBuffer` 推送，见第 18 章 |

Flask 是引用最多的第三方包（145 次），说明 Web 层在代码里的分布广度——它不只是"一个入口文件"，而是与业务逻辑交织在一起，这也是 `backend` 目录膨胀到 188 个文件的原因。

会话没有放在进程内存里，而是落在 MySQL 的 `flask_sessions` 表。这样重启进程不会踢掉已登录用户，代价是每次请求多一次数据库读。

## 数据存储

**主库：MySQL。** 通过 PyMySQL（12 次引用）连接，用 DBUtils 的连接池（`PooledDB`）管理连接，游标类型为 DictCursor（查询结果直接是字典）。连接池上限、autocommit 策略与事务包装见第 21 章。

**被测算系统的数据库：多驱动适配。** 引擎除了自己的主库，还要连被测算系统（SUT）的数据库来做数据轨校验。支持的驱动按引用次数排列：

| 数据库 | 驱动 | 引用次数 |
|:---|:---|---:|
| PostgreSQL | psycopg2 | 4 |
| 崖山数据库 | yaspy | 4 |
| Oracle | cx_Oracle | 2 |
| SQLite | 标准库 `sqlite3` | — |

驱动分派集中在一个入口，按 `db_type` 选择实现，见第 11 章。

**向量存储：不用独立向量库。** 这是本项目一个明确的技术决策。检索用的向量存在 MySQL 的 `rag_chunks` 表里，相似度在 Python 进程内用余弦计算。选它的理由是：不引入 ChromaDB 这类外部服务，部署时少一个组件；数据量在单机场景下可接受。代价是召回性能不如专用向量库，无法支撑大规模并发检索。

## 浏览器自动化

**Playwright ≥ 1.40**（12 次引用）是唯一被采用的浏览器自动化方案，没有 Selenium 或 Puppeteer 的痕迹。选它的理由：原生支持等待与自动重试、支持多浏览器内核、对现代前端框架（异步渲染、虚拟 DOM）的兼容性优于 Selenium 的显式等待模式。引擎在此基础上做了两件事：一是用 CDP（Chrome DevTools Protocol）补充浏览器内部控制能力；二是封装了统一的动作执行层（见第 9 章、第 15 章）。

## 大模型接入

这一层是引擎的智能来源，也是选型最复杂的地方。核心模块在 `src/ai/`（28 个文件），设计上有四个特点。

**第一，多 provider 并存。** `src/ai/ai_providers/` 下四个实现：

| 文件 | 覆盖的服务 |
|:---|:---|
| `ollama.py` | 本地 Ollama |
| `deepseek_openai.py` | DeepSeek（OpenAI 兼容协议） |
| `openai_compat.py` | 任何 OpenAI 兼容端点 |
| `anthropic.py` | Anthropic |

上层不直接调这些实现，而是经过 `src/ai/router_module/` 的路由层。路由层的设计原则写在它的文档串里：**每类任务独立配置 provider 和模型，互不兜底；用户指定什么就用什么，成功就成功，失败就失败。** 这句话的含义是：系统不做"云端失败就偷偷切本地模型"的静默降级——因为那会让结果不可解释，同一条用例今天跑用云端、明天跑用本地，判定基准就漂了。

**第二，任务类型感知。** `src/ai/router_module/task_types.py` 定义了七种任务类型：

```
REQUIREMENT_ANALYSIS   需求分析
TEST_CASE_MODELING     用例建模
TEST_DESIGN            测试设计
OPERATION_INSTRUCTION  操作指令
COMPLEX_REASONING      复杂推理
VERIFICATION           校验与幻觉检测
GENERAL                通用
```

每种任务类型可以独立指定 provider 与模型。这个设计让"拆需求用一个模型、判断言用另一个模型"成为配置问题而不是代码问题——例如把校验任务指向推理能力更强的模型，把通用任务指向便宜模型。

**第三，模型注册与定价。** `src/ai/model_registry.py` 负责模型列表拉取、缓存（24 小时过期，落 JSON 文件）、后台每日刷新，并提供"模型名 → 是否支持视觉输入"的推断（`is_vision_model`）。`task_types.py` 内另有一张 `_MODEL_PRICING` 定价表，按输入/输出 token 单价和档位（local / budget / premium）分类。定价表的用途是成本核算，与 `src/ai/pricing_fetcher.py`、`src/ai/token_estimator.py` 配合，把 token 消耗折算成费用。

**第四，不可用性熔断。** `src/ai/llm_circuit.py` 是进程级单例的熔断器：连续失败 2 次触发熔断，冷却 240 秒。它的存在理由写在模块文档里——语义辅助调用每次都要付满云端超时（20 秒）才能降级，而多步用例（14 步 × 20 秒）在模型不可用期间会直接撞穿单用例 300 秒的墙钟预算。熔断把这个"模型是否可用"的判定收敛成单一事实，下游只读，不各自重推。

## 检索与嵌入

嵌入模型的获取有三条路径，按配置项 `embed_provider` 路由：

| 取值 | 实现 |
|:---|:---|
| `disk` | 本地 `sentence_transformers.SentenceTransformer`（4 次引用），模型缓存在 `models/sentence-transformers/` |
| `ollama` | 调用 Ollama 的 `/api/embed` |
| `cloud` | 经 AI 路由层以 `embedding` 任务类型调用云端 |

三条路径都失败时，退化为一套基于 n-gram 哈希的 128 维向量。这个兜底保证检索层不会因为嵌入服务不可用而整体崩溃，代价是召回质量下降。详细机制见第 16 章。

## 配置与校验

**配置**用 PyYAML（7 次引用）读 YAML，用标准库 `json` 读 JSON。配置分四层，见第 22 章。

**入参校验**用 pydantic v2（3 次引用）定义请求模型，用 jsonschema（2 次引用）做响应契约的深度校验。jsonschema 的引入有明确动因：缺少完整 JSON Schema 校验时，嵌套类型不匹配会被漏检，产生假通过。

**凭据加密**用 cryptography（3 次引用）的 Fernet 对称加密。用户凭据（大模型 API Key 等）加密后存储，与业务配置分离。

## 设计取舍

**为什么不把 AI 调用抽象成"统一客户端"。** 路由层没有做成"一个函数屏蔽所有 provider 差异"，而是把 provider 与任务类型的映射显式化。代价是配置项变多；收益是**没有任何隐式降级**——日志里能明确看到"这次校验用的是哪个模型"，出问题时可以归因。测试工具最怕的就是"看起来通过但说不清是谁判的"。

**为什么不用独立向量库。** 引入 ChromaDB 或 Milvus 会增加一个部署组件和一套数据一致性问题（向量与 MySQL 里的原文可能不同步）。当前规模下，MySQL 存向量 + 进程内余弦是够用的，且原文与向量始终在同一事务域内。这是一个"规模换简单"的取舍，规模上去后需要重新评估。

**为什么依赖清单没有收敛。** 这是一个明确的工程债：28 个已声明包未使用、11 个在用包未声明。前者的代价是安装体积和潜在版本冲突，后者的代价是**在新机器上按 requirements 装完会跑不起来**。第 26 章会说明实际的部署路径是否绕开了这个坑。
