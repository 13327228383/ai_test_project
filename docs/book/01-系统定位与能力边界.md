# 第 1 章　系统定位与能力边界

## 概述

这套系统的核心断言是：**测试执行策略应当由数据的完整度决定，而不是由代码里的分支决定。**

传统自动化测试有两种做法。一种是步骤驱动：把用户操作拆成固定步骤脚本，脚本写死每一步点哪里、输什么、断言什么。它确定、可复现，但需求一变就要改脚本，而且它只验证"脚本作者想到的事"。另一种是意图驱动：给执行器一句自然语言描述（"验证用户能用错误密码登录时看到提示"），让执行器自己想办法完成。它灵活，但结果不可复现，判定标准模糊——同一个意图跑两次可能得到两个结论。

这套引擎选的是第三种：**用例本身是结构化的数据，执行策略从这个数据的完整度里读出来。** 一条用例长这样：

```
TestCase {
  case_id: "...",
  actions: [ {type, target_hint, value}, ... ],      // 结构化操作序列
  checks:  [ {track, precision, check, expect}, ... ] // 结构化验证点
}
```

`actions` 和 `checks` 是否齐全，决定了这条用例怎么跑。这个判定集中在 `src/pipeline/steps/step4/strategy_router.py` 的 `_select_strategy`（第 30 行附近），策略常量定义在同文件第 22–25 行：

| 常量 | 值 | 含义 |
|:---|:---:|:---|
| `STRATEGY_SKIP` | 0 | 数据异常，跳过 |
| `STRATEGY_DETERMINISTIC` | 1 | 确定性执行 |
| `STRATEGY_AI_EXPLORATION` | 2 | AI 自主探索 |
| `STRATEGY_PURE_ACTION` | 3 | 纯动作执行 |

## 系统做什么

一句话：**把需求文档转成可执行的结构化用例，在真实运行的系统上执行，产出带证据的判定结果。**

完整链路分五步：

1. **Step1 需求数据拉取**：从配置的数据源（本地文件、接口文档平台、设计稿平台等）取回需求原文，落库。
2. **Step2 需求拆解**：把长文档切成短片段，逐片段提取"操作 → 预期反馈"的结构化需求条目，与原文逐字核对，防止大模型编造文档里没有的需求。
3. **Step3 用例建模**：把需求条目转成可执行用例，包括操作序列与验证点，落库。
4. **Step4 混合执行**：按数据完整度选执行策略，在浏览器、接口、数据库三个通道上执行并判定。
5. **Step5 报告**：汇总执行结果，算通过率，产出缺陷报告与人工补测建议。

## 系统不做什么

划清边界比列举功能更重要，否则会把系统的承诺读大。

**它不是"给个网址就能测"的黑盒。** 它需要需求输入。没有需求文档，Step2 无从拆解，后面的用例也没有依据。它不会自己去猜这个系统应该有什么行为。

**它不保证覆盖业务逻辑的正确性。** 它验证"需求文档写的行为是否成立"，不验证"需求文档本身写得对不对"。如果需求漏了一个分支，系统不会因为它漏了就补上。

**它的 AI 部分有明确的成本与不确定性。** Step4 的策略 2（AI 自主探索）会真的调用大模型多轮决策，这部分执行慢、成本高、且依赖模型能力。系统通过预算约束（轮数、页面指纹、交互次数、墙钟时间四重限制）收敛它，但不能消除它。

**单机单实例。** 后端是单进程 Flask 应用，执行槽位有限，不是分布式测试平台。

## 三种执行策略

这是全书最核心的一张表。它在第 29 章展开，这里先给出结论。

| `actions` | `checks` | 策略 | AI 调用 | 适用情形 |
|:---:|:---:|:---|:---:|:---|
| 有 | 有 | 确定性执行 | 0 次 | 需求里给了完整的操作和验证标准，执行器照做 |
| 无 | 有 | AI 自主探索 | 多轮 | 需求说了预期行为，但没说怎么操作（例如"用户应当能看到订单列表"） |
| 有 | 无 | 纯动作执行 | 0–1 次 | 只给了操作序列，没写验证标准 |
| 无 | 无 | 跳过 | — | 数据异常 |

三条策略的关键约束是：**它们共用同一条验证管道。** 策略只决定"怎么产生执行步骤"，不决定"怎么判定结果"。判定统一走 `src/pipeline/steps/step4/verification/` 的校验层，最终由终判函数按置信度阈值归一为一个结论。这条约束避免了"确定性路径判通过、AI 路径判通过"两套标准并存的口径分裂。

## 检查点模型

一个检查点由四个字段定义：

```
{ track, precision, check, expect }
```

- `track` 决定它在哪个通道验证：`ui`（界面）、`api`（接口）、`db`（数据库）。
- `precision` 决定它怎么判定：`exact` 走规则（比对状态码、SQL 结果、DOM 内容），`fuzzy` 走大模型辅助判定。
- `check` 是检查项类型，取值来自一张全局注册表，执行端只认注册过的类型。
- `expect` 是期望值，可以是文本、数值或结构。

第 30 章会说明为什么"精度"要独立成一个字段，而不是按通道各写一套判定逻辑。简要说：同一个断言（例如"页面上出现成功提示"）在不同的需求语境下，判定严格程度不同；把精度作为数据属性而不是代码分支，能让校验层保持单一实现。

## 结论的四种状态

执行结果不是通过/不通过两值，而是多值。`executions` 表的 `status` 列记录了每条用例的最终状态：

| 状态 | 含义 |
|:---|:---|
| PASS | 检查点全部通过，且置信度达到阈值 |
| FAIL | 检查点判定不通过 |
| SKIP | 前置条件不满足导致未执行，例如目标页面不存在、无有效断言 |
| ERROR | 执行过程本身出错，例如执行器抛异常、检查项类型未注册 |

这个划分是有意的。把"没跑"和"跑了但不过"混在一起，会掩盖两类完全不同的问题：前者是测试环境或数据的问题，后者是被测系统的问题。第 32 章会说明把 ERROR 和 FAIL 分开的必要性——早期版本曾把执行器异常也记成"产品有缺陷"，产出了假 Bug。

## 设计取舍

**为什么以 `TestCase` 为唯一资产格式。** 系统内部不自建第二套用例格式，也不在流水线中做格式转换。需求拆解、用例生成、执行、报告四层读写的是同一个结构。代价是这个结构的字段必须一次设计到位，扩展时要改多处；收益是任何一层都不会因为格式转换丢失语义。

**为什么允许两条生成路径（规则与 AI）。** Step3 既有确定性规则生成，也有大模型生成。这不是设计冗余，而是刻意的分工：规则路径负责高频、可预期的用例形态，成本为零且结果稳定；AI 路径负责规则覆盖不到的需求。第 7 章会给出两条路径的实际分工与各自的代码入口。

**为什么不追求"零 AI"。** 系统的定位是"通用 + 智能"，不是"确定性脚本引擎"。完全去掉 AI，需求拆解和用例生成就退化成关键词匹配，遇到文档写法稍有变化就失效。系统的做法是把 AI 放在它擅长的位置（理解自然语言需求、判定模糊断言），把它的不确定性用置信度和人工审核闸门兜住。
