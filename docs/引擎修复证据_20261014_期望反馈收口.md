## 2. 根因：RC-AL

`infer_expected_feedback`（`src/pipeline/step3/_rule_extractor_keywords.py`）**只按 operation 关键词猜文案**，
其推断产物被**固化进 `requirements.expected_feedback` 列**，下游（断言构造 / 极性闸门 / 场景分类）
**直接当需求义务使用，且从不调用该函数已有的 `declared` 极性自洽分支**。三类错得离谱：

1. **负向需求配成功文案**
   - REQ-040「登录**失败**…需提示'用户名或密码错误'」→ 库存 **`登录成功,欢迎`**
   - REQ-041「viewer **不允许**新增/编辑/删除（403 权限不足）」→ 库存 **`新增成功,添加成功,创建成功,保存成功`**
   - REQ-050「服务端验证失败时返回错误提示（flash 红条）不写库」→ 库存 **`操作成功,成功`**

2. **只读需求配成功文案**（分页/统计/过滤/内置账号本就不弹"操作成功"）
   - REQ-039 内置账号 · REQ-042 分页 · REQ-043 统计 · REQ-045 过滤 → 均 **`操作成功,成功`**
   - 页面事实是资产列表页 → 断言"页面文本含'操作成功'"**结构性不可满足** → 系统性假 FAIL

3. **SSOT 的 `declared` 分支从未被调用** —— 极性自洽逻辑写好了，消费端绕过。

**证据**：库里 `requirements.expected_feedback` 与 `requirements.operation` 逐行对照（REQ-039/040/041/042/043/045/049/050）。

## 3. 修复（一处实现，三个消费点）

- 新增 `resolve_expected_feedback(operation, declared, description)`（唯一实现），判定次序：
  1. **极性为负** → 返回"自身即表达拒绝语义"的原文（declared 优先于 operation）；
  2. declared 非空**且非推断产物**（`is_inferred_feedback`）→ declared（需求自述为权威）；
  3. 其余 → `infer_expected_feedback`，其中**只读型（无变更动词 且 有只读语义词）返回 `""`** = 不产文本型反馈。
- 收口点 1：`requirement_store/__init__.py::_parse_row_to_req`（需求行→需求对象的唯一入口）。
- 收口点 2（最初漏、关键）：`case_store/crud/write.py` 落库层**曾自己 `SELECT expected_feedback FROM requirements`**
  （第二份实现）→ 改为带 operation/description 并调同一 SSOT。
- 配套：`_fallback_cases` 探针极性改为 `expects_error_feedback(expected or operation)`
  （原 `operation + expected` 会被描述防护机制的"拦截"误导）。
- **RC-AM（Fix H 泛化）**：`_check_guard.ensure_post_action_triggers` 的判据由
  「断言类型白名单」→「**断言级极性**」（读 `check.expected`，而非恒为模板文案的用例级字段）。

**生成层已确认**：039/042/043/045-E01 → `expected_feedback=None`，断言退化为 `no_error`（结构性，不再假 FAIL）；
040-E01 → 期望=登录失败原文，动作=fill 用户名/密码 + click 登录；
049-E01 → 期望=拦截原文，validation 场景；UX02 动作含 **`check:name=confirmed`**。
