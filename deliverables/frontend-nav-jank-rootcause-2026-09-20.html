最关键发现：修复前 app-design.css 里存在一条"侧栏交互门"规则 html:not([data-sb-ready="1"]) .sidebar .nav-item { pointer-events: none }， 但全仓库没有任何代码去设置 data-sb-ready——门被焊死了，没有任何"开闸"逻辑。 效果就是侧栏菜单项永久不可点击。这解释了为什么"修了几十次"仍在复发：每次修的是别的部分，而这扇门一直关着。

一、症状与复现路径

用户报告：切换功能区（左侧菜单）时卡顿、无反应、UI 混乱，且"这个也修了几十次了"。

拆解成三个可观测现象，各自独立可复现：

  • 无反应：点击菜单项无任何跳转 —— 命中测试显示点击落在 .sidebar-section 容器上，而不是菜单项本身。
  • 卡顿：每次切页都"先按一种皮肤画好、约 160ms 后整页换皮"，字号从 1× 变成 1.3×，侧栏被整体重排。
  • UI 混乱：菜单在首帧之后被反复改动（服务端渲染的展开态 → DOMContentLoaded 被重置 → 鉴权返回后再按权限过滤），用户看到菜单"自己动"。

另有第四个隐藏问题：步骤区徽标换行导致下方全部菜单下移 64px——用户在菜单上停留点击的瞬间，目标已经移走。

二、根因链（含证据）

根因 1（决定性）· 悬空交互门：CSS 设了门，JS 没有任何开闸

用同一张页面上做 A/B 对照：一组保持 data-sb-ready="1"（修复后状态），一组移除该属性（还原修复前状态），然后用 elementFromPoint 对菜单项中心点做命中测试。

状态计算 pointer-events命中元素菜单项可点击性
修复后（属性=1） auto A.nav-item nav-item--dash active A.nav-item[/dashboard] 可点击 ✅
还原修复前（属性缺失） none DIV.sidebar-section A.nav-item[/dashboard] 点不动 ❌
恢复属性后复测 auto A.nav-item nav-item--dash active A.nav-item[/dashboard] 可点击 ✅
移除属性后，菜单项的 pointer-events 变成 none，命中落到容器 DIV.sidebar-section—— 这正是修复前全仓库的真实状态。也就是说菜单不是"偶尔点不动"，而是根本点不动。

静态证据：git grep -n "data-sb-ready" HEAD -- src/ 仅命中 app-design.css 三行（规则定义），无任何设置该属性的 JS/模板代码。

根因 2 · 首帧后换皮重排：字号缩放变量在首帧之后才写入

app-design.css 中所有字号令牌都是 calc(12px * var(--ui-scale, 1)) 形式，默认 --ui-scale: 1；而用户的个性化配置是 1.3。 修复前，这个 1.3 只在 /api/bg-config、/api/input-style 返回后（首帧之后约 160ms）才写到 <html> 行内样式——于是每次切页都是：先按 1× 画完整页 → 再整体放大到 1.3×。

实测位移：侧栏高度 966px → 1154px，菜单项整体下移最多 126px，40 个菜单项全部位移、最大 1625px。

修复：在 CSS 之前用同步内联脚本恢复"上次真正生效的配置快照"（localStorage e2e_boot_cfg_v1:<uid>），首帧即最终皮肤； 主脚本拿到接口响应后与快照做差异比对，完全一致就一个变量都不写（零 DOM 变更、零重排），只有用户真的改了配置才写。

同时把"背景绘制"与"布局变量"彻底分开：背景只写 <html> 背景与 <body> 透明（不影响布局尺寸，可安全重放）， 并在 pagehide 清理背景轮播定时器，避免多定时器叠加反复重绘。

根因 3 · 步骤区徽标换行，把下方菜单整体推走 64px

步骤徽标文案会从"等待 / 0"变成"已完成 / 3"。在 --ui-scale: 1.3 下，徽标一旦换行，.step-item 被撑成两行， 步骤区高度从 161px 涨到 225px（+64px），其下方所有菜单项随之整体下移 64px。

修复（纯防御性、与业务无关）：.step-badge { flex-shrink: 0; white-space: nowrap }， .step-label 加省略号。状态文案的变化从此不可能影响布局高度。

根因 4 · 侧栏"三时机定型"，用户看到菜单自己动

侧栏定型原本分散在三个时机：① 服务端 Jinja 渲染 .expanded；② DOMContentLoaded 里 initSidebarSections 重置展开态并注入导航项；③ 鉴权返回后按权限过滤隐藏菜单项。用户视觉上就是"菜单一会儿这样一会儿那样"。

修复：收敛为唯一入口 A.initSidebar()（幂等），一次做完：注入导航项 → 首帧权限过滤 → 展开态/滚动恢复 → 开交互门。 权限首帧用本地缓存渲染（注释与代码明确：该缓存只用于渲染，绝不参与鉴权/授权判断）。 页面初始化改为单次生命周期（_pageInitDone 标志），兼容浏览器前进/后退缓存，避免重复初始化。

另加两个用户体感增强：展开态与滚动位置记忆（跨页保持，用户不需要每次重新找位置）；折叠态下"当前页所在分区"标题高亮（避免反复点开多个分区找位置——这正是菜单反复位移的诱因之一）。

三、修复是"通用"的，不是补丁

三个根因分别在令牌层、结构层、交互层，修复也落在对应层，与任何具体页面/业务无关：

层修复机制为什么通用
令牌层首帧配置快照 + 差异比对闸门作用于 <html> 级 CSS 变量与配置应用器，所有 48 页共用同一套；不针对某个页面
结构层侧栏统一幂等定型入口 + 交互就绪门只依赖 .sidebar/.nav-item 这些通用结构约定，与菜单内容无关
布局层徽标/标签禁止换行针对"状态文案长度变化"这一通用风险，而非某句具体文案
交互层本地状态记忆（展开态/滚动/项目下拉/用户名）任何页面都能复用同一份状态键，新增页面自动受益

同时保证不引入新的"死锁"：交互门有三重开闸——正常路径 initSidebar() 结束即开、主脚本 1.2s 兜底、模板内联脚本 1.5s 独立兜底（即使主脚本加载失败也不会让菜单永久不可点）。

改动文件：app-common.js、app-design.css、_layout_base.html，并同步重算前端布局锁 FRONTEND_LOCK.json 的指纹（8 分区结构未变，verify_lock.py 校验通过）。

五、残余与后续建议

  • 内容区异步渲染引起的 CLS：33 页切换中 2 页 CLS > 0.1（/dashboard(0.1602)、/quality-panel(0.2388)）。不影响菜单可点性，建议后续给图表/列表容器预留固定高度（骨架屏）。
