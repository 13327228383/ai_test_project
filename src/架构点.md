# 架构点：测试用例驱动的混合执行引擎

> **版本**: v3.1 | **日期**: 2026-06-26

---

## 核心结论

本系统是**测试用例驱动的混合执行引擎**——以结构化测试用例 `{actions, checks}` 为核心资产，以单管道三策略为执行模型。

不是传统步骤驱动（死板），也不是纯意图驱动（模糊）。而是根据**数据的完整度**自动选择执行策略：数据齐全走确定性（零 AI），只有检查标准走 AI 探索，只有操作走基础验证。

---

## 当前架构模型

```text
需求文档
    ↓ Step1 拉取
纯文本 + RAG
    ↓ Step2 拆解 (5+1步防幻觉)
{operation, expected_feedback, source_quote}
    ↓ Step3 用例建模 (AI + RAG)
{cases: [{actions, checks: [{track, precision, check, expect}]}]}
    ↓ Step4 单管道三策略
        ├─ actions+checks → 确定性执行 (零AI)
        ├─ checks only → AI探索 (checks=成功标准)
        └─ actions only → 纯动作+基础验证
    ↓
[执行证据 + 三轨校验] → 通过/失败
    ↓ Step5 报告
```

---

## 分层定位

| 层级 | 核心对象 | 地位 |
|:---|:---|:---|
| 资产层 | `TestCase {actions, checks}` | 核心测试资产，持久化到 `test_cases` 表 |
| 策略层 | `steps_from_case()` | 数据完整度 → 三策略路由，零分支 |
| 执行层 | `browser_core` + `verification` | 确定性/探索/纯动作 三条路径共用同一验证管道 |
| 验证层 | 三轨校验 (ui/api/db) | exact → 检查器 / fuzzy → AI辅助 |
| 报告层 | check 粒度结果 | 可追溯到原文引用 |

---

## 三策略决策表

| 条件 | 策略 | AI 调用 | 典型场景 |
|:---|:---|:---:|:---|
| `actions` + `checks` 齐全 | 策略1 确定性执行 | 0 次 | RAG 有完整 API/SQL/页面信息 |
| 只有 `checks`，无 `actions` | 策略2 AI 自主探索 | 多轮 | 需求描述了预期行为但不知道怎么操作 |
| 只有 `actions`，无 `checks` | 策略3 纯动作执行 | 0-1 次 | 只有操作序列但没写验证标准 |
| 都没有 | 跳过 | — | 数据异常 |

**关键约束**：三种策略走同一条验证管道（`_build_verify_step()` 共用），不做第二条执行路径。

---

## 术语边界

| 传统表达 | 本系统表达 | 含义 |
|:---|:---|:---|
| 测试用例 | TestCase | `{case_id, actions, checks}` 结构体 |
| 测试步骤 | actions | 结构化操作序列 `[{type, target_hint, value}]` |
| 检查点 / 断言 | checks | 结构化验证点 `[{track, precision, check, expect}]` |
| 通过率 | check 通过率 | 按检查点粒度统计，非用例粒度 |
| 模糊验证 | fuzzy check | AI 辅助判定（VLM/LLM），标 `precision: fuzzy` |
| 精确验证 | exact check | 规则判定（SQL/状态码/DOM），标 `precision: exact` |
| 用例建模 | Step3 case_generator | AI + RAG 生成完整 TestCase |
| 用例执行 | Step4 steps_from_case | 三策略路由 | Step4 入口 |

---

## 设计原则

1. **资产以 TestCase 为核心**：`{actions, checks}` 是系统唯一测试资产格式，不做格式转换。
2. **策略由数据决定，不由代码分支决定**：`steps_from_case()` 检查数据完整度 → 选策略，不是 if/else 新旧格式。
3. **验证管道只有一条**：exact / fuzzy 是 check 属性，管道结构不变。`_build_verify_step()` 三种策略共用。
4. **RAG 信息必须利用**：给了表名写 SQL，给了接口写路径——不要"忍住不写"。
5. **AI 探索有边界**：策略2 的 AI 收到的是结构化 `checks[{track, precision, check, expect}]` 清单（不是自由文本），完成后走同一验证管道（不是自由心证）。

## 数据模型命名约定

| 旧名（已废弃） | 新名 | 位置 |
|:---|:---|:---|
| `validation_intents` | `test_cases` | SQL 表 |
| `intent_meta` | `case_meta` | SQL 表 |
| `intent_requirement_mapping` | `case_requirement_mapping` | SQL 表 |
| `intent_id` | `case_id` | SQL 列 |
| `intent_type` | `case_type` | SQL 列 |
| `intent_generator` | `case_generator` | Python 模块 |
| `model_validation_intents` | `model_test_cases` | Python 函数 |
| `steps_from_intent_schema` | `steps_from_case` | Python 函数 |
| `what_to_check` | `checks[{check, expect}]` | 数据结构 |

**保留不改的**：`browser_intent_parser/` 是 Step4 运行时模块名（不是数据模型），保留。

## 一句话定位

**测试用例驱动的混合引擎：数据全走确定性，数据不全走 AI 探索，但永远只有一条验证管道。**
